# 版本提醒与一键更新（2026-10-01）

状态：创始人已确认（11 条全部照准）。目标：clone 了 GitHub 仓库的用户知道有新版本，并能安全地一键更新。

## 1 发布与版本（流程，不是代码）
1. 版本号沿用 semver，下一版 0.5.0；界面显示「版本 0.5.0 · 10月1日」（日期取该版 CHANGELOG 标题）。
2. 只有 GitHub Release（tag `vX.Y.Z`，在 origin/main 历史上）才算更新；更新只到发布过的 tag，不到 main 最新提交。
3. 仓库根 `CHANGELOG.md`，每版一节：`## 0.5.0 · 2026-10-01`，下分 `### 新东西` `### 修好的` `### 需要你做的`（中文）。发布由主会话在推送时写。README「更新」一节加「Watch → Custom → Releases 订阅邮件」。

## 2 检查
4. 服务启动 1 分钟后查一次，之后每 24 小时一次；设置页「检查更新」手动查。方法：`git fetch --tags origin`（30 秒超时），取 origin 上可达 origin/main 的最高 semver tag，与本地版本（package.json version）比较。只读公开仓库，不上传数据。设置项「自动检查更新」默认开。
5. 有更新：看板最上方（在「等你拍板」之上）一条安静提示「有新版本 0.5.0 · 看看更新了什么 · 更新」；早上的待办摘要（SessionStart 简报）带一句。「这个版本先不更新」按版本记住，下一版再提醒。
6. 检查失败（连不上 GitHub、不是 git 仓库等）：只在设置页「更新」一栏写原因，不弹窗、不上看板。
7. 本地 HEAD 不是目标 tag 的祖先（本地比发布版新或已分叉）→ 不提示（创始人自己的机器就是这样）。

## 3 更新
8. 预检，任一不满足不动手，回一句人话原因：是 git 安装（否则「请按 README 手动更新」）；当前分支 main；已跟踪文件无本地修改（未跟踪文件不管）；HEAD 是目标 tag 的祖先；没有正在运行的写稿/剪辑/发布任务（`~/.autocrew/chief-editor/runs.json` 里 running、发布进行中等——按现有判断「重启前查活跃轮次」的逻辑复用）。
9. 过程：记下旧 HEAD → `git merge --ff-only vX` → 安装依赖（与 README 一致的 npm ci，含前端所需）→ 构建前端 → 重启服务 → 健康检查（60 秒内首页 200）。由服务拉起一个独立的更新进程执行（服务自己会被重启），日志写本机目录 `update-<时间>.log`。页面显示「AutoCrew 正在更新，大约 1 分钟」，轮询服务回来后自动刷新（1b 起登录跨重启不掉）；随后弹出该版更新说明，「需要你做的」突出显示。
10. 任一步失败 → 自动退回旧 HEAD（预检保证工作区干净，`git reset --hard <旧 HEAD>` 安全）→ 重新安装依赖、构建、重启 → 提示「更新失败，已退回 0.4.x，原因：…，完整记录在 <日志路径>」。不能停在半新半旧。退回本身也失败 → 停下并给出手动恢复命令。
11. 防重复：本机目录锁文件；更新中再点 / 再跑 `autocrew update` → 「正在更新」。更新触发路由只收同源浏览器会话（模型 / MCP / bearer 不能触发）；命令行 `autocrew update` 是本机用户操作，允许。

## 4 不做
不做自动静默更新；不更新到未发布提交；不处理 Windows；不上传任何统计。
