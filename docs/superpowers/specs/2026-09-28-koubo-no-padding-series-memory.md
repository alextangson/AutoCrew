# 口播稿不硬凑、不重复：补料、系列记忆、手法库、提炼门槛（v2）

- 日期：2026-09-28
- 状态：v2 已吸收 codex 评审（5 个 P1、8 个 P2、1 个 P3，逐条对照见第 8 节）。**2026-09-28 创始人已定稿**，第 7 节 4 条全部拍板。
- 已做完的前置：档案写作规则清理（23 条里停用 7 条，保留 16 条，其中改写 5 条），档案篇幅改为「7–10 分钟 / 约 2000–2800 字」。资料库 `creator-profile.json`，改前备份 `creator-profile.backup-20260928-before-rule-cleanup.json`。

## 1. 为什么要改

创始人 09-28 拍学院系列时念出了三个问题：
1. **长度硬凑**：「很多的文案要硬凑，但跟主题内容没什么关系」。
2. **跨稿重复**：「我们说的那个 agent，就是你电脑上跑的那个，哪家都无所谓，这句话很多都出现，我是很反感这种」；每篇结尾都是「短期看、长期看」。
3. **中心思想撞车**：「"AI 要听的是你图什么"这一条，它的内容跟"说写小红书"那条有什么区别？没什么区别」。

根因（v2 按 codex 核对后修正）：

| 现象 | 根因 |
|---|---|
| 硬凑 | 口播包里其实已经有「每段带新信息、不靠重复凑时长」的规矩（`koubo.ts:53`），审稿也有「模板填充」判据（`script-review-prompt.ts:27`）。**问题出在执行和材料**：写手没有一个「先列信息点、不够就去补料」的流程，材料不够时只能拿话去填。v1 说「没有任何环节检查」，这个说法不准确。 |
| 跨稿重复 | 写作包看不到这个账号最近写过什么；自有素材只按话题相关度拉取（`own-material.ts:347`），不按时间，也不整理说过的内容 |
| 骨架一样 | 选中的立意卡会规定「只用这一种骨架」（`script-prompt.ts:450`），通用结构菜单只能排在它后面；再加上零散的反馈规则被当成每篇必有的段落 |
| 规则堆积、互相打架 | 自动提炼的规则直接进写作包；同一条规则从第二个平台来时，会在 `creator-profile.ts:283` 原地升级成全局规则（v1 写错成了 distiller 的行号）；规则没有稳定 ID，工作台按数组下标去改 |

## 2. 目标、不做的事、首版范围

**目标**：每条稿子围绕自己的中心思想展开到 7–10 分钟，长度靠材料撑满；同系列连看几条，不会听到意思相同的样板话，也不会看到同一副骨架。

**不做**：
- 不降时长。
- 不新增后台模型调用。现有 style-distiller 的后台提炼这次不改，只把它的产出改成先待批。
- 不自动改已经拍了的稿。
- 不做爆款预测。

**首版范围**（采纳 codex 建议，先做最小有效的四件）：
1. 一个统一的「稿件摘要」对象；
2. 领包时冻结一份「近期稿件快照」；
3. 在现有审稿台上扩展，让它能记录按意思比对的结果；
4. 一个真正由创始人控制的规则审批入口。

手法库（C 节）同时做内容，但不挡前三件上线。

## 3. 四个改动

### A. 篇幅靠补料，不靠凑

**写作流程**（写进写作包，属于宿主的流程要求；服务端证明不了写手真的先规划、后动笔，只能检查交上来的东西）：
1. 动笔前先写一句中心思想，列出信息点并注明类型：真实案例、往下挖一层的原因、完整演示、反方意见和边界、创始人亲历。每条估个时长。
2. 估出来够 7 分钟就写。
3. 不够就按顺序补：先领补证任务，自己查、抓页、核对、入账（这是一串动作，不是调一次就能拿到案例）；再把原因往下挖一层；再请创始人补。
4. 仍然补不上，就交回一个「缺口记录」，不交凑出来的稿。

**缺口记录**（新增，可以恢复）：
- **内容**：已有什么材料、缺什么、要创始人回答什么、对应哪个写作包。
- **写入**：沿用现有的认领令牌和串行队列。稿子保持 `drafting` 或 `revision`，认领继续有效；缺口一直没人回，认领到期后自动释放。
- **恢复**：创始人补了材料或改了要求，按现有的 `pack_request_changed → force` 重领写作包，不沿用旧的快照。

**稿件摘要 `outline`**：新领的写作包，交稿时**必须**附上：中心思想一句、信息点清单、骨架（怎么开头、怎么推进、怎么收尾），以及按意思记下的「说过的东西」——解释过的概念、下过的判断、用过的比喻和例子，每项一句话。旧写作包不要求，缺失时按兼容路径处理。

**「凑数段」判据**：
- **判 blocker 的**：这段删掉以后，中心思想、理解和节奏都不受影响，也没带来新的事实、原因、做法或必要的过渡。
- **放过的**：叙事铺垫、必要的转场、帮观众理解的类比。
- **写法**：审稿人用短引文定位这一段，再说明它的范围，并写清「它没贡献什么」。

**长度提示**：
- 跟门禁的失败结果完全分开，不打回，也不扣修复次数。
- 字数统计口径：正文去掉空白后的字符数。
- 上下限优先用本次要求，其次用档案。档案里的 `wordCount` 是自由文本，解析不出数字就返回「未知」，不去猜下限。
- 估时只是规划信息，不能证明材料真实或充分。

### B. 系列记忆和按意思的重复检查

**快照的范围**（口径写死）：
- **平台**：同一平台。平台字段缺失的稿，不进快照。
- **状态**：只收 `draft_ready`、`approved`、`editing`、`publish_ready`、`publishing`、`published`。删除稿、归档稿、本篇都不收。
- **时间**：看每条稿最后一次进入上述状态的时间，最近 30 天内；按这个时间倒序、再按 content_id 排序，保证稳定。最多 10 条。
- **同题多版**：同一选题、同一平台有多个版本的，只取最新的一版。
- **账号**：首版假设一个资料目录只对应一个创作者账号，这条写进文档。

**快照里每条带什么**：
- 标题；
- 一个标签：「已发」或「待发（写过，观众还没看到）」；
- 这条的 `outline`；
- 没有 `outline` 的老稿，只放首尾各一段原文，并标注「覆盖不足：中段不在比对范围内」。

**快照冻结**：
- 领包时把快照冻结下来，记录每条稿的 `content_id`、`draft_hash` 和摘要版本号。
- 同一个包重复领取，拿到的还是这份快照，不会悄悄换掉比较的依据。
- 手法卡目录的版本也一起冻结。

**写作包里的用法说明**：
- 已发稿里解释过的词可以直接用；待发稿里解释过的，照常讲，因为观众还没看过。
- 最近用过的开头和收尾，这条换一种。
- 中心思想要能一句话说出和快照里每一条的区别，说不出就停下来问创始人。
- 这份记忆只是去重参考，不当事实证据，也不当成观众已经知道的前提。

**按意思的重复检查**（审稿人判断语义，服务端只校验结构）：
- 审稿包附上冻结的快照。审稿人逐条比对新稿，找出意思上已经说过的东西。
- **判 blocker 的**：样板式解释换了说法、主线判断跟快照里某条实质相同、用过的比喻或例子再次当主菜。
- **放过的**：为了讲新东西顺带提一句的旧概念；明确的承接（这种只能承接已发稿）。
- **审稿结果要扩展**（沿用现有审稿台）：新增「系列比对」一栏，写明比对的是哪份快照（快照 ID）、查了哪几条、哪几条覆盖不足；每个重复问题写明对应快照里哪条稿的哪一项；每个放过的地方写明理由。
- **服务端只校验结构**：引用的稿件和条目必须在这份快照里，比对覆盖要完整。新格式的审稿不能交一个空的 `issues:[]` 就算查完了。
- **快照过时就补审**：审稿结论落地前，服务端核对同平台有没有新稿进入这个范围。有的话，要求补审新增的那几条，不直接追认通过。「核对加登记」要一步完成，中间不能被另一条稿插进来。

**状态不能当证明**：`draft_ready` 或 `accepted*` 不代表去重已经通过。现有流程里，修订次数用完仍有 blocker，也会以 `accepted_with_issues` 进入 `draft_ready`。验收看这一版实际的系列比对结果。自审照旧标成自审，不算独立评审，也不算创始人采纳。

### C. 手法库（内容和代码分开走）

**跟现有的区别**：现有的爆款拆解卡（`pattern-store.ts`）不动，仍然只作参考，不叠加成必须满足的结构要求。手法库是单独的一个库。

**优先级**：创作者的明确要求 > 已选立意卡的骨架 > 手法卡。要真正换掉骨架，需要**在立意阶段**生成候选卡时，就给它看手法目录和系列快照，让不同的卡用不同的打法。只替换写作包里的结构菜单不够。

**卡片治理**：
- 每张卡有稳定的 ID 和版本号，草稿目录和已审目录分开放。
- **书籍卡**：注明书名、作者、版本、能核对的位置（章节、页码）。只写了书名，不算核对过出处。
- **创始人经验卡**（这次停用的 3 条规则就属于这一类）：标注来源是创始人历史改稿；作用范围首版只限这个资料目录，不随产品发给所有用户。以后要发给所有用户，先经创始人授权。
- **示意**：卡里的示意案例明确标注「这是示意，不是事实材料」。

**怎么用**：
- 写作包里列出已审目录，每张卡一行。
- 提供一个按 ID 和版本号读取全文的只读入口，宿主读得到，不依赖服务端的文件路径。
- 交稿时的 `technique_ids` 要逐个校验存在，并记下用的是哪个版本。
- 允许一张卡都不用。
- 两张卡 ID 不同，不代表骨架就不同；两张卡也可能冲突，由写手取舍，并在 `outline` 里说明。

**首批**：12–15 张，书目为《让创意更有黏性》《疯传》、麦基《故事》、《金字塔原理》、一本脱口秀写作的书（待定）。另外把创始人经验里的 3 条做成经验卡。卡片由宿主起草，创始人逐张过目后，才进入已审目录。

### D. 自动提炼的规则先待批，而且只有创始人能批

**规则的数据结构**：
- 每条规则有稳定 ID、revision、状态和来源证据。状态分四种：`active`（生效）、`pending`（待批）、`rejected`（丢弃，保留一条墓碑记录，以后蒸馏再提出同一条就直接挡掉）、`disabled`（停用）。
- 存量规则没有 status 字段时当作 `active`，**但保留 `disabled:true`**，这次停用的 7 条不能复活。
- 新产出的提炼规则必须显式标成 `pending`，不能借「缺字段就当旧数据」的兼容逻辑自动转正。
- 蒸馏时依据的证据要落盘，给创始人审的时候能看到这条规则是从哪几处改稿来的。

**升级也是提案**：同一条规则从第二个平台来时，另建一份「升级为全局」的提案。原来那条平台规则保持原样、继续生效；批准了提案才真正升级。

**只有创始人能批**（这是 P1）：
- 规则要生效，必须依赖**服务端能验证的用户操作事件**：绑定规则 ID、revision 和决定，并且幂等。模型自己报的 `user_confirmed:true`、复述的「用户原话」、把来源标成 `user_explicit`，都不算批准。
- 对话里在宿主侧没有可信的用户消息通道，服务端分不清是创始人点的头还是模型填的字。所以**首版只在工作台批**：对话里可以列出待批规则、提醒创始人去工作台批，但不能从对话里批。
- 旧的写规则入口也要过同一道门：`chat-router.ts:1035` 的 `add_style_rule`、`editorial.ts:148` 的 `user_confirmed`，以后都只能产出 `pending`。
- 认领令牌只证明谁在写这篇稿，不证明创始人批准。

**生效规则统一读取**：只有一个函数负责取出生效规则，初稿、整稿修订、选区改写（`selection-rewrite.ts:50`，现在直接读全部规则）、画像生成等所有把规则当写作指导的地方，都走这一个函数。选区改写的平台从目标稿件上取，不再把所有平台的规则都注进去。管理列表可以显示待批规则，但不渲染成写作要求。

**写档案要串行**：所有规则写入都走同一个档案存储接口，带上预期的 revision，原子写入，统一排队，防止创始人审批和后台蒸馏同时写、互相覆盖。首版明确「单写者」约束：同一个资料目录只允许一个 AutoCrew 进程写，写进文档，启动时检查。

**不因待批规则重领包**：写作包的指纹只算本平台实际生效的写作配置，不算待批规则、审批日志和无关的更新时间。有规则被批准后，照现有机制明确提示重新领包，不偷偷塞进旧包。

## 4. 提交契约（新字段必须全程贯通）

`outline`、`technique_ids`、缺口记录这些新字段，要贯穿工具参数、校验、`SubmitPayload`、同号提交的指纹（`writer-submit.ts:102`，现在只算标题、开头、正文、结尾、标签）、`PendingReview`、Content 和版本记录（`local-store.ts:863`，现在只在标题或正文变了才记新版本）。

- 现有 `draft_hash` 的含义不变，免得影响发布等下游环节。另外新增一个「审稿上下文指纹」，把摘要、快照 ID 和手法卡版本都算进去。
- 正文改了、摘要没跟着更新（包括选区改写、回滚），就把摘要标成失效，退回用原文节选比对；不静默沿用旧摘要。
- 旧写作包走明确的兼容路径。

## 5. 边界和异常

1. **创始人的覆盖只作用于他指定的那一项**：指定了开头，就只豁免开头；指定时长，不豁免主张重复；指定结构，不豁免主菜重复。每个豁免都要记下对应的用户决定，宿主不能自己宣布豁免。
2. **账号还没有历史稿**：快照为空，写作包显示「暂无」。
3. **老稿没有摘要**：只放首尾原文，标注覆盖不足；不让模型现场回填。
4. **补料补不上**：交缺口记录，见 A 节。
5. **意思重复的误判**：顺带一提、明确承接的，可以放过；放过要写理由，创始人可以推翻。
6. **手法卡出处核不到**：这张卡不进已审目录。
7. **规则待批期间**：写作包照常领，不因此提示要求已变化；一直没人批，就一直不生效。
8. **多平台**：快照只看同一平台，平台字段缺失的稿不进快照。
9. **并行写两条稿**：领包时冻结的快照看不到对方，靠审稿落地前的「快照过时补审」来兜住。
10. **快照的篇幅**：最多 10 条，每条摘要控制在固定长度内，超出就截断，并标注被截断了。

## 6. 验收

- 用新流程改写 7 条还没拍的稿：会议纪要、短一点、提示词工程已死、公司上 AI、技能 50 遍、文档漂亮、对打卡。
- 7 条最终版本固定后，**两两比对共 21 对**，按意思比：没有样板式解释、没有实质相同的主线判断、没有重复当主菜的比喻或例子；每一处放过的都写了理由。中途任何一条改了，跟它相关的比对就作废重做。
- 7 条的中心思想各写一句放在一起，创始人要能一眼分清。
- 骨架有没有机械重复由人判断，不看手法卡 ID 重不重复。
- 创始人读完 7 条，判断还有没有硬凑的段落（人工判）。
- 规则审批：模型带着 `user_confirmed:true` 调任何入口，都不能让一条 pending 规则生效（写成自动化测试）。

## 7. 创始人拍板

1. 系列记忆：最近 30 天、同平台、最多 10 条（已定）。
2. 重复检查：按意思判，审稿人做；服务端只校验结构（已定）。
3. 手法卡首批 12–15 张，书目见 C 节（已定）。
4. 规则审批：**首版只在工作台批**，对话里只能列出待批规则、提醒创始人去工作台批（创始人 09-28 确认。codex 指出服务端分不清是创始人点的头还是模型填的字，对话批准挡不住模型代批）。

## Implementation notes（2026-09-28 实现时的取舍，按节记）

**接手说明**：在 Codex 中途取消的 19d9ebc 上继续。保留了它的大方向（规则状态字段、工作台审批路由、快照冻结进写作包、outline/technique_ids 字段），改掉了四处不对的地方：删掉了公众号 `min_chars/max_chars` 门禁和 12000 字拒收（口播本来就没有字数门，那两处是别的平台的现有行为，删了是越界）；把「所有稿件写入改成全局一把锁」退回按稿件 id 串行，只在「进入系列范围」和「审稿核对+登记」两处取系列锁；`saveProfile` 不再偷偷把规则改成待批（模型可达的入口本来就不经过它）；摘要失效改成按正文指纹现算，而不是写时清空。

**D 规则**
- 规则状态由 `ruleStatus()` 统一判定：有 `status` 按 `status`；没有的存量规则 `disabled:true` → 停用，否则生效。新代码每次写规则都把 `disabled` 跟状态对齐（非 active 一律 `disabled:true`），这样还在跑旧代码的进程（例如没重启的 :4317）读到待批规则也会跳过。
- 存量规则的稳定 id 在读侧按「下标+文本+创建时间+作用域」算出来，第一次写入时落盘；不改它们的状态。
- 唯一生效入口：`POST /api/rules/decision`（`src/desktop/rule-approval.ts`），只认浏览器会话 cookie + 同源 + JSON，具名 MCP bearer 和 `/api/invoke` 都进不来；绑定 `ruleId + revision + decision`，`eventId` 幂等，同一 eventId 换内容报冲突。`style:update_rule`（IPC，bearer 可达）只能改文本（回到待批）、停用、或申请启用（待批），不能批准。
- 升级提案：自动提炼的同一文本在**另一个平台已生效**时才起提案；原平台规则待批或停用时不起（免得给创始人堆重复待批项）。用户在 editorial 里明确点名平台的长期偏好（`scope:"platform"`）按他说的平台另记一条待批规则，不走升级。批准提案 → 提案生效为全局、原平台规则停用。
- 丢弃只能丢「待批」的规则；已生效的走停用。丢弃是墓碑，以后同文本（不论作用域）再提直接挡掉。
- 写档案：`mutateProfile` 读改写整段进同一资料目录的队列，temp+rename 原子写，`revision` 每写 +1；`saveProfile` 整份保存时比对 revision（读出来的档案一定带 revision；从零构造的整份档案按覆盖处理）。`updateProfile` 不再接受 `writingRules`。
- 单写者：`desktop/server.ts` 启动时在资料目录写 `.autocrew-writer.lock`（pid）；另一个活进程占着就**告警不拒绝启动**（误判把创始人挡在门外代价更大）；持有者进程已不在就接管。
- 画像生成用 `rulesForPlatform(profile, null)`（所有平台的生效规则），选区改写按目标稿件平台取，没传 content_id 时只给声音内核。
- 测试夹具 `src/modules/profile/rule-fixtures.ts` 里有 `addApprovedRuleForTest`（记一条 + 以工作台决定批准），只给测试用，产品路径不调用。

**B 系列记忆**
- 「进入上述状态的时间」取 `seriesEnteredAt`：从白名单外转入白名单时记（白名单内部流转如 draft_ready→approved 不刷新）；老稿没有这个字段时退到 `publishedAt`（已发）/`draftReadyAt`/`updatedAt`。
- 同选题的**其他版本**不进本篇的快照（那是这篇自己的前身，不是系列里的另一条）；其他选题同平台多版本仍按「只取最新一版」。
- 每条摘要进快照的上限 1500 字符，按 thesis → 骨架三项 → said 顺序装，装不下的截断并标 `truncated`；points（估时规划）不进快照。没有有效摘要的老稿只放首段/末段各 300 字，标覆盖不足。
- 摘要有效性按正文指纹现算：`outlineDraftHash` 等于当前 `draftHash` 才有效。编辑器改稿、选区改写、回滚到别的版本都会让它自动失效、退回原文节选，不需要写时清空。
- 快照过时的判定：冻结之后有**新稿进入范围**，或范围内已有的稿**正文变了**（draft_hash 变化）。「待发→已发」这种标签变化不算。
- 补审方式：服务端把新增的几条并进审稿单的快照（新 snapshot_id），审稿人重交时 `checked` 要覆盖新快照全部条目，已查过的可以沿用原结论。这比「只交新增几条」多一点重复，但结构校验保持一种口径。
- 原子性：`transitionStatus` 目标是白名单状态时，先取系列锁再取单稿锁；审稿台 `submit` 整段在系列锁内（写手队列 → 系列锁 → 单稿锁，顺序固定）。`saveContent` 直接把新稿建在白名单状态（手工导入）这条路没有取系列锁，窗口极小，首版不处理。
- 系列比对结果存在 `Content.seriesReview`，带 `reviewContextHash` 与记录时间；审稿通过/草稿就绪本身不代表去重通过。engine 审稿（显式 `review:"engine"`）和 `review:"none"` 不产出系列比对，`seriesReview` 为空即「这一版没做过」。
- 快照、手法目录冻结在写作包里；同一包重复领取原样返回。有缺口记录的包不再原样复用，force 重领时重新冻结。

**A / §4 提交契约**
- 新契约包 = 写作包里有 `series` 字段。交稿缺 `outline` 是拒收（`code:"outline_required"`），不记 attempt、不扣修复轮。旧包没有该字段，照旧可不带。
- 同号提交指纹：带了 outline 或 technique_ids 才把它们加进指纹；两者都没带时沿用旧算法，升级前记下的 attempt 重放不会被误判成冲突。审稿台的提交指纹同理（带了 series_review 才算进去）。
- 审稿上下文指纹 `reviewContextHash = sha256(draft_hash, 有效摘要, 快照 id, 手法卡 id@version)`，`draft_hash` 含义不变。摘要或手法卡变化会记新版本，并把这几项写进版本记录；快照 id 变化只进指纹，不单独记版本（补审换快照不是改稿）。
- 长度提示 `length_hint` 出现在每个交稿回执里，`advisory:true`。字数口径是 hook+body+cta 去空白后的字符数；上下限只认「N-M 字」这种写法，先看本次要求再看档案 `wordCount`，写成「7–10 分钟」这类没有字数的就是 unknown。
- 缺口记录：`autocrew_writer gap{content_id,pack_id,gap:{available,missing,questions},claim_token}`，走原有写门（认领令牌）和写手队列，写进写作包和稿件；稿件保持 drafting/revision。之后同包 `pack` 返回 `pack_request_changed`（带 gap），force 重领拿新包新快照；下一次成功交稿清掉稿件上的 gapRecord。

**C 手法库**
- 卡片格式：`src/modules/writing/technique-store.ts` 的 `techniqueCardSchema`（id、version、name、purpose、source{book|founder_experience}、verification{status: 已核|部分待核, note, links}、fits、notFor、moves、illustration{label:"示意，不是事实材料", text}、misuse、pairing）。
- 已审目录有两处来源：产品内置 `src/modules/writing/techniques/approved/`（只许书籍卡，混进创始人卡直接报错）+ 资料目录 `<library>/techniques/approved/`。`drafts/` 永不加载。
- 2026-09-28 创始人批准的 15 张已转换：12 张书籍卡进内置已审目录；3 张创始人经验卡按 §3 C「只限这个资料目录」放在 `src/modules/writing/techniques/founder-library/`，**没有写进创始人的资料库**（实现时不碰 `~/AutoCrew资料库`）。要启用这 3 张，把这三个 json 复制到 `~/AutoCrew资料库/techniques/approved/` 即可，这一步留给创始人。
- 标「部分待核」的卡原样保留核对状态，不因批准改成「已核」。
- 读全文：`autocrew_writer technique{content_id?,id,version}`，有 content_id 时读该稿写作包冻结的那一版。
- 立意阶段：宿主路径（scout angles 任务包）和 engine 路径（runAngleStage，仅在明确给了资料目录时）都会带上系列快照和手法目录。
