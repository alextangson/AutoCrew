## 3. 唯一目录与文件职责

### 3.1 项目身份与位置

```text
<library>/
  autocrew-library.json
  shared-assets/                         # 跨项目、版本化的公共素材
  workspaces/<workspace_id>/
    topics/                              # 尚未开写的选题与其调研
    research/                            # 选题级、跨稿件共享的来源原件
    library/                             # 常备素材及业务登记记录
    project-registry.json                # content_id 与项目位置的业务绑定
    projects/
      YYYYMMDD 初始标题--<完整content_id>/
        .autocrew-owner
        AGENTS.md                        # 生成的项目操作约定
        项目信息.md                       # 生成的只读视图
        项目导航.md                       # 按中文名称导航，不复制产物
        00-project/
          autocrew/                      # 仅 AutoCrew 写：正文元数据、状态、版本索引等 JSON
          notes/
            workflow-state.json          # AutoCrew 生成的恢复视图
            execution-reports/           # 服务接收的执行事实与恢复记录
            migration/                   # 清单、路径映射、迁移与恢复收据
        01-script/
          references/                    # 本稿采用的原始材料、摘录、来源快照
          research/                      # 本稿采用的简报、立意、调研过程
          evidence/                      # 证据台账、正文引用定位、出处清单
          manuscripts/                   # 每版文稿；版本号不重排
          reviews/                       # 审稿与改稿记录
          handoff/gNNNN/                 # 不可变：交接单、定稿、来源与决定快照
        02-aroll/                        # 原始口播、转写、粗剪与对应字幕
        03-broll/                        # 项目专用镜头、图片、屏录、分镜与生成记录
        04-edit/                         # 可携带工程、时间线、恢复映射、工作导出
        05-audio/                        # 配乐、音效、音轨、授权与来源
        05-cover/                        # 封面母版、历次方案与当前配对
        06-publish/
          copy/                          # 分平台文案
          packages/                      # 冻结的发布包、文件清单
          receipts/                      # 平台结果、URL、截图等实际证据
          metrics/                       # 发布后数据快照与采集时间
        07-delivery/                     # 获批准的交付版本与交付清单
```

保留已有 `05-audio` / `05-cover` 名称，避免仅为编号整齐而大改剪辑引用；00–07 是流程分组，不要求每个数字只出现一次。目录分类只有上述这一套。

目录日期取首次建项目日期；标题用于人阅读，完整 `content_id` 防止重名碰撞。后续修改标题不自动改目录名。业务身份由 `(library_id, workspace_id, content_id, project_id)` 决定，不能靠文件夹名称推断。

`project-registry.json` 是必要的业务绑定清单，保存相对工作区的 `project_relpath`、`layout_version`、`binding_revision`，不保存正文、检索倒排数据或模型向量。`.autocrew-owner` 保存同一组身份供双向核验。两者不一致就停止；缓存丢失不能成为新建第二个项目的理由。

一份媒体不因每轮修改重复复制。必要的原件快照、批准版本与可编辑母版按版本、用途和哈希登记；这是同一项目的版本记录，不是第二套工作目录。

一个 topic 的多个平台稿仍保留既有 `siblings`、各自 `content_id` 与状态；不让多条内容争用一个 owner。公共原片进入常备素材/共享素材后可按稳定素材编号引用；项目选用的版本冻结，不能因另一平台稿更新而被替换。

### 3.3 正文与状态的唯一来源

为保留现有 Content 契约，AutoCrew 管理的 JSON 仍是正文、版本与业务状态的权威记录，但它也位于**同一个项目**的 `00-project/autocrew`。`manuscripts/`、项目信息和账本 Markdown 是确定性导出，标明源版本/哈希，不做双向文件同步。

Claude 通过 writer/scout/editorial 工具提交，服务在同一事务中更新权威记录及项目文件；不直接覆盖导出稿。需要接收人工编辑的 Markdown 时，走显式“导入为新版本”，保留旧稿和审稿失效规则。Codex 不改这些文稿。

服务事务以事务日志、提交版本和恢复步骤处理多个普通文件；不能声称 NAS 上的多文件 rename 天然是数据库事务。写作接口只有在本次文稿/台账导出已完成时才返回“项目同步完成”；中断重试复用同一请求编号与版本，不重复交稿、不重复耗费生成额度。

## 4. 从开写到交接的行为

### 4.1 建项目时间

- 未开写的纯选题不建项目，仍属于 `topics/`。
- `autocrew_writer pack` 分配或复用 content_id 后，在开始备料、返回写作包前完成 `ensureContentProject`。只建一次，重领包、修改标题、重试和更换宿主都复用。
- 首次 submit、人工导入稿、后台引擎生成等入口走同一层兜底检查，不能绕过；不能只改 Claude 主路径。
- 失败时不返回已成功分配的项目路径，不落到当前工作目录；预分配的内容编号保留可恢复记录，重试不另造一条稿。
- 包回执新增项目身份、`project_root`、只读文稿与约定文件路径；路径由服务解析，不信任调用方指定的其他根。
- 写作所采用的 topic 调研在这里冻结到 references/research；共享的原始来源仍可复用，但本稿来源快照必须可恢复。重新调研不得静默覆盖旧稿采用的材料。
- 纯图文稿至少建立 00-project、01-script、06-publish；配图、封面、交付目录按实际需要创建，不要求 A-roll，不误入视频状态机。

### 4.2 handoff 复用规则

handoff 先读取该 content_id 的正式绑定，再检查 owner、资料库、白名单和稿件审核门。传入 `project_root` 仅允许与已绑定根相同，用于兼容旧调用；不同则返回 `project_binding_conflict`，不能复制出第二个项目。

`paths.ts` 继续执行真实路径、按路径段比较、项目为 `projects/` 直接子目录、项目内不允许符号链接、文件存在与归属匹配等检查。写稿时由 AutoCrew 建立的 owner 与剪辑时的 owner 是同一种协议，无须重新认领目录。

`video.json` 只有明确的 ENOENT 才能采用该资料库约定的项目根；无权限、I/O 错误和配置损坏必须报错，不能使用当前 catch-all 的默认回退。已经有绑定的项目目录丢失也不能被 `mkdir` 当作新空项目补建。

A-roll 先复制/校验进入 `02-aroll`，已有本项目原件就按哈希复用。handoff 的媒体事实仍经过画面、音轨、时长等现有验证；等待 A-roll 不妨碍前期写稿建项目。

## 5. 交接单：冻结事实，不替剪辑做方案

交接包由 AutoCrew 生成，位于 `01-script/handoff/gNNNN/`。至少包含：

| 文件 / 字段 | 约定 |
| --- | --- |
| `handoff.md` | content_id、project_id、平台、创始人确认的目标时长、当前有效代次、稿件/材料哈希、创始人对剪辑说过的原话、固定登记说明 |
| `final-script.md` | 对批准版本的 UTF-8 原字节快照；不 trim、不重排换行、不移除字符、不重新生成。不因模板定界符而改稿；正文作为材料文件读取 |
| `decisions.json` | 创始人确认的标题与封面字、确认依据、时间、适用的稿件版本/哈希。修改稿件后重新判断是否失效，不从最新生成稿推断“拍板” |
| `sources.md` / `citations.json` | 本稿采用的每个数字断言、归因引述 → 正文定位 → 证据编号 → 原文链接、原话、来源类型与材料快照 |
| `manifest.json` | 协议版本、稳定项目身份、generation、draft_hash、A-roll 哈希、决定与出处映射哈希、各文件相对路径/哈希、备注摘要哈希 |

交接单不写分镜、镜头安排和画面建议；已有调研材料中的示例也不能伪装成创始人的剪辑指令。Codex 的分镜产物由剪辑工作流另存 `03-broll`。

标题、封面字、平台、目标时长没有确认值时明确列缺项，由写稿侧补齐；AutoCrew 不自动按字数估计一个“创始人目标”。出处缺口也不能靠编造原话或 URL 补齐。

现有 `evidenceLedger` 只登记证据，**不等于已经逐句完成正文映射**。需增加与定稿哈希绑定的 `citations`：正文段落/原文片段和位置、证据 id、原文 URL、quote、sourceType、核查结果。新的数字或“某某说”没有对应项则阻止新 handoff；定位越界或定稿已变也阻止。

第一人称经历、推算和用户材料保留 `own_claim` / `user_claim` 的真实等级及依据，显示“无外部原文／未外部核验”，不冒充外部已核验证据。外部事实缺少所需原文链接与原话时回写稿侧处理；明确批准的个人经历按自身来源类型记录。自动规则只能检查覆盖与字段，语义是否受原文支持仍须写稿侧审查，不能把自动通过称为全面事实核查。

交接包仍不可变且受大小预算约束：大体积原材料放 `01-script/references`，包内写相对引用和哈希，不截断定稿或出处来挤进预算。

新清单 v2 的哈希不含某台机器的挂载绝对路径；身份使用 library/workspace/project/content，文件使用项目相对路径和内容哈希。API 根据当前挂载点返回可用绝对路径。来源、拍板文字、定稿或 A-roll 有变化必须另起有效代次，不覆写旧包。

## 6. 状态、审批和两个宿主的权限

### 6.1 单一状态来源

业务状态、有效交接、最终登记、gate1–4 审批结果和持久恢复信息由 AutoCrew 服务保存。`项目信息.md`、`project-manifest.json`（若保留兼容）、`00-project/notes/workflow-state.json` 均生成自服务记录，带 `generated`、来源 revision/hash，不接收反向手改。

导出视图被手改时报告漂移，重新导出；不把“文件里写了 approved”当成真实审批。现有工作树权限下，这是服务协议和可检测约束，不宣称能阻止拥有 NAS 任意写权限的外部程序篡改所有文件。

### 6.2 保留可恢复工作，不依赖聊天记忆

需要增加受限的 `autocrew_video report`，否则将 workflow-state 变成只读后，Codex 无处保存恢复资料。它仅接收：真实宿主任务/session ID、编辑器 project/timeline ID、进程/生成 job ID、字幕及时间线对应关系、素材路径与哈希、执行结果、费用/订阅额度记录、错误和下一步。

`report` 必须验证当前内容认领、执行机器、绑定版本与交接代次，并幂等保存。它不能接受写入 `Content.status`、`gates.*.approved`、发布状态或稿件正文的补丁。自然语言 phase/完成声明最多是待核验报告。

人工审批仍来自创始人的实际确认。已有的真实批准消息、时间、产物哈希可沿用并登记来源，不因文件搬家重复要求审批；不能验证的历史批准只记为待核实，不能自动补时间、补原话或改 pending 为 approved。宿主提交的原话是证据输入，不能仅因它自称“创始人已同意”就取得新的审批权限。

gate3 / gate4 的批准记录由 AutoCrew 保存后生成恢复视图。`register` 继续验证当前交接、认领、路径、媒体和两道产物哈希，并比对服务保存的对应批准记录；成功才按原状态机推进。这里需要服务端记录批准事实的入口：创始人在工作台确认，或接入可验证真实用户消息的现有宿主确认通道。缺少可信批准来源时先保留报告，不用 Agent 自填标记替代。

### 6.3 宿主范围

- Claude：用已有写稿/证据/审稿/交接工具提交；不直接改机器管理的状态 JSON。
- Codex：写剪辑媒体、工程、分镜、封面与交付文件；新增受限 report 以保存执行事实；通过 register 回登记，不获得写稿、审稿或对外发布权限。
- Codex 可以保存授权工作产生的发布辅助文件，但共享目录本身不授予外部上传/点击发布权，也不扩大现有 `mcp/host-policy.ts` 的发布能力。
- 发布侧通过 AutoCrew 保存文案、发布包与真实回执；文件存在和 Agent 回复“发布了”都不等于 published。

## 7. NAS、本机缓存与多机器

### 7.1 NAS 放什么

NAS 只放普通持久文件：Markdown、JSON/JSONL 业务记录、媒体、可携带的时间线/工程导出与恢复说明。业务台账、来源和绑定清单不是可丢弃的检索索引。

全文/向量检索索引、SQLite 及 WAL/SHM、数据库锁、缩略图缓存、代理媒体、编辑器运行数据库放在：

`<machineRoot>/libraries/<library_id>/workspaces/<workspace_id>/cache/` 或对应剪辑软件的本机应用数据目录。

当前没有数据库就不为本改造额外引入数据库。将来新增检索存储必须走本机路径解析器；本机索引可从活动资料库的业务记录重建，索引缺失不丢内容、不重置状态。外部软件必须本机运行的工程数据库不直接搬上 NAS；项目保存可导出的工程/时间线和恢复映射，保留已验证所需的本机依赖。

当前用户在本地项目工作，NAS 只接收完成项目的已验证归档副本；两边不能同时作为可编辑正本。其他用户直接在 NAS 工作时，软件确需本机代理/缓存可按 project_id 建立受控缓存，回传产物需校验。不能以清理缓存为由删除独有源片。

### 7.2 活动资料库不可用

本地工作时，NAS 未挂载只阻止归档，不阻止写稿和剪辑。其他用户选择 NAS 活动库时，NAS 断连适用以下停写规则。

每次建项目、写业务记录、发布代次、登记产物前检查资料库身份、连接、可写性与写者占用。挂载丢失、根被删、身份改变或项目绑定丢失时返回明确错误并停写，不能回退 `~/Projects/broll`、程序目录、cwd 或默认 `~/.autocrew`。

本机缓存可以显示带“离线/可能过期”标记的已有信息；不能据此批准、派工或发布。已经提交的外部生成任务保留 job ID 和恢复记录，不重复计费提交；NAS 恢复后重新校验再入库。

### 7.3 两台机器谁能写

初版采用**单台执行机器、单个 AutoCrew 写服务**。资料库的 `.autocrew-writer` 独占记录标明机器、进程、nonce；第二台机器不能启动另一写服务、领取直接落盘的剪辑任务或修改项目文件，只可查看。

现有目录锁需要补充写入时的 nonce 复核；断连重连后失去原占用的进程必须停写。项目级认领也记录实际执行机器与会话，避免同一个“codex”宿主名被两台机器同时使用。合作的 Agent 和剪辑器只在持有执行权的机器写。

异常残留不按超时自动抢锁，不用远端 PID 推断对方已死。切换执行机器需要先确认旧服务和剪辑写入已停止，再释放占用并在新机重建索引/连接配置。网络分区期间不自动接管。

当前本地服务只监听本机，不能假定第二台机器的 localhost 能访问第一台；本 spec 不自动开远程端口或扩大访问权限。后续经明确配置的安全远程接入仍共用同一写服务，不能演变成两个 NAS 写者。没有按此协议接入的 Finder/外部编辑器并发写入无法仅靠 MCP 锁消除，检测到变动就停止受影响提交。

## 8. 存量素材绝对路径

磁盘上受管素材路径继续以工作区相对路径保存；API 为调用者解析成当前挂载位置下的绝对路径。项目内资产也采用项目相对路径，拒绝 `..`、符号链接逃逸和其他项目归属。

| 旧记录情况 | 转换与展示 |
| --- | --- |
| 指向本资料库内存在的文件 | 校验身份和文件后转换相对路径，不复制同一文件 |
| 指向库外、文件可读 | dry-run 列出；复制到明确的受管素材位置，SHA-256 一致后登记相对路径，源文件进入恢复清单 |
| 原挂载前缀失效，但能用稳定素材编号和已有哈希匹配 | 展示重定位候选及匹配证据；明确、唯一匹配才转换，不按文件名猜 |
| 文件缺失、无权限、多候选或哈希不符 | 原记录保留，显示“待重定位/文件缺失/无法访问”的实际原因和原路径；不伪装为已转换、不静默删记录 |

所需素材有未解决问题的项目不能提交迁移、handoff 或 register。无关素材的问题可独立列为未完成项，不能以局部成功宣称整个资料库完整迁移。数据库/索引命中不能替代文件实际存在与哈希验证。

## 9. 历史迁移能力（本轮取消，仅供另行授权时使用）

### 9.1 先形成可审阅的 dry-run

命令名称在实现时确定；能力必须包括 `plan/dry-run`、按已批准清单 `apply`、`resume`、`verify`、`rollback`，不能让 dry-run 顺便创建项目或改状态。

清单至少包含：

- 资料库身份与根；旧 `contents/<id>`、已存在的 `projects`、明确范围内的 broll 与既有 NAS 归档。
- 每个 content_id ↔ 旧目录 ↔ 新目录 ↔ project_id 的对应，归属证据和待确认项。
- 每个文件的来源、目标、大小、SHA-256、复制/复用/重定位/排除理由；重复文件、同名不同内容、失效引用、符号链接和数据库候选。
- 内容/版本/正文哈希、写作包 pack_id/attempt/review 状态、认领与真实会话、有效交接代次、已登记产物、人工闸门、待运行任务、费用/额度台账。
- 本机剪映草稿、ChatCut 项目/时间线、XML/时间线 JSON、外部素材及共享视觉资产的依赖；不能用一份项目目录清单假装包含所有编辑器资产。
- 空间需求、迁移停写窗口、恢复位置、每个进行中项目的恢复检查，以及旧活动目录退出方式。

若将来明确授权包含 Jev 的迁移，其 `needs_binding` 必须在该次 apply 前解决：创始人指定已有内容，或明确批准导入为新 content_id。新导入需保留原 project_id 为来源身份；真实定稿/审核证据缺失就列待补，不虚构已审状态以绕过 handoff 门。已存在的 NAS 年份归档是否纳入该批迁移、哪份为正本也必须列清，未列入的历史目录保持原样。

### 9.2 停写、复制、校验、提交

1. 获准后暂停本批稿件的写入与派工，等待写作提交、register 事务及编辑器保存完成；持有资料库独占锁。进行中的外部 job 可以保留任务，不重投，但提交结果在本批切换前不得写旧根。
2. 保存源布局版本、绑定清单、权威状态、认领和恢复点。源清单重新核对；与获准计划不同就重新预览，不偷偷扩大迁移范围。
3. 在资料库内唯一的迁移暂存区复制文件，逐文件 SHA-256 对照。此时不改原件、不启用新绑定。改写的仅是明确识别的结构化路径字段；自由文本、批准原话、定稿和不可变旧交接包不做全局替换。
4. 生成新绑定、项目 owner、只读视图和必要的 v2 交接。维护迁移日志与唯一 migration_id。发布前再校验源文件列表和哈希，发现活跃写入则停下。
5. 以可恢复提交步骤发布新项目及绑定、布局版本。新版本读取层只认已提交的那一套，不能 union 合并两套目录；中途崩溃由迁移日志恢复，不能凭哪个目录存在就选哪个。
6. 逐项目执行读取、继续写作包/交接、编辑器恢复和登记核验。记录字节验证与真实软件打开结果，二者分开。
7. 全部通过后，旧活动目录移到明确的恢复隔离区，登记“已迁走”，不保留旧根 symlink 指向新项目，不再作为日常可编辑副本。原件删除属于最后独立步骤，仅在明确授权范围和恢复验证完成后执行。

迁移暂存与恢复副本是有清单的短期恢复材料，不注册为第二个活动项目。切换后只有新根能被 writer、handoff、register 解析。没有通过恢复验收的项目不算迁移完成。

### 9.3 进行中项目怎样接着干

| 项目情形 | 必须保留 / 如何继续 |
| --- | --- |
| 写作包已领、等待交稿或审稿 | 保留 content_id、pack_id、attempt、请求指纹、证据配额、修订轮数及真实宿主归属；恢复后继续当前有效包，不因迁移重领、重复扣额度。旧包原本已失效则照原规则拒绝 |
| 已有稿，等待 A-roll | 新根已建立，状态不提前变 editing；A-roll 到来后第一次 handoff 使用原绑定 |
| 已派工、有效 v1 handoff 含旧绝对路径 | 原交接文件与哈希原样入历史，不原地改写。服务在迁移事务中发出 g+1 的 v2 交接，记录 supersedes/relocation 原因，旧有效清单与旧认领令牌失效；编辑宿主保持不变，向同一实际任务返回新定位与凭据。内容仍是 editing，不伪装成重新审稿或重剪 |
| 已有 workflow-state / 正在剪辑 | 导入 job、时间线、字幕对应、费用、gate 证据和 next_action；保存原文件原字节历史副本，再生成新只读视图。代码认识的路径按迁移表重定位；未识别的私有工程不盲目文本替换 |
| gate3 已过、gate4 未过（Jev 当前情况） | 核验同一成片字节和真实 gate3 依据；继续保留 gate4 pending，从封面审核接续，不借迁移自动登记或发布 |
| 已 register / publish_ready / published | 保留既有 register_hash、审批、发布回执和历史交接，不重登记、不重发布。用独立 relocation 映射解析历史资产的当前位置；原始不可变记录保留，重放成功回执返回新的可用定位 |
| 批准的成片/封面字节未变化 | 批准继续对应同一哈希，无须因搬家重新走创意审核 |
| 搬迁或工程重连导致时间线、字幕或成片字节变化 | 作为真实产物变化处理，重新核验受影响部分；不能自动重算“批准哈希”填回旧批准 |

旧工作会话恢复时先向 AutoCrew 查询有效 project_root 与 generation，不能按聊天历史中的绝对路径继续写。迁移期间持有旧 binding_revision 或 generation 的迟到写入返回 `project_relocated` / `stale_handoff`，附只读恢复指引；不会把旧请求写到新目录后假装成功。

g+1 的迁移发行是“相同已获准内容的存储重定位”专用服务操作，不开放给 Agent 绕过稿件审核、A-roll 或人工闸门。若旧内容/媒体/审批本就不满足要求，则清楚阻塞，不能用迁移特例补成已批准。

### 9.4 外部编辑器、共享资产和回退

- 同一视频继续使用既有剪映草稿或 ChatCut project/timeline ID，不因迁移创建完整新工程。先保存可恢复导出，再用软件支持的重定位/重连方式验证媒体、时间线和匹配 SRT。
- 旧正文或历史包里出现的绝对素材链接不通过全文替换“修复”。保留原文与哈希，由内容/媒体读取层根据明确的旧路径→稳定素材→新位置映射解析；导航展示当前链接。不能一边声称定稿未改，一边重写正文中的链接。外发发布包需要的资源 URL 转换沿用发布导出层，不能倒灌成新定稿。
- NAS-only 工程不被软件支持时，软件工作数据库/代理留本机；NAS 项目中的导出和恢复映射负责耐久保存。未证明可重建的本机依赖不得删除。
- 老 broll 约定引用的 `assets/visual-bible`、人物、字体、Logo 等不能因为离开父目录而丢失。dry-run 枚举本批采用的版本，复制/核验到资料库 `shared-assets` 或冻结项目引用；不借此搬空整个 broll 共享库。
- 回退先停写，并保留切换后新增工作；只允许在没有新提交时按原绑定恢复。已有新提交须基于日志前向修复或生成新的回退清单，不能直接覆盖为旧备份。每个回退动作可重入且有结果记录。

当前用户沿用 lifecycle 的“本地工作、之后 NAS 归档”策略，受管项目额外要求保留 AutoCrew 业务记录及有效路径；不修改全局技能。直接使用 NAS 活动库的其他用户无需同盘搬家。

## 11. 实现范围与顺序

1. 项目存储边界：统一 `ensure/resolve/projectPaths`、业务绑定、owner、布局版本、写者/项目认领校验；不让各工具自己拼路径。业务状态规则独立于 NAS 和缓存实现。
2. Content 存储适配：`local-store.ts` 及直接拼 `contents/<id>` 的读写方统一经过该边界。包括 MCP resources、IPC、正文/版本、封面/素材 HTTP、发布、复盘、检索输入、写作包和 register 的素材登记；不能只替换 contentDir 就宣称全部完成。
3. 写作与调研：`writer-prepare/pack/submit`、引擎与导入入口、`host-evidence-store`、brief/evidence 读写；实现项目创建、稿件采用快照、逐版导出与出处映射。
4. 剪辑交接：`video-handoff.ts`、`handoff/{roots,paths,handoff,manifest,types,register,register-artifacts,register-commit}.ts`；v1 历史兼容、v2 清单、目录复用、审批记录与恢复报告。正式登记不再把整个交付件再复制到旧 contents 树。
5. 状态入口：受限 report、真实批准事实登记、只读视图生成、主机白名单与通道契约。保持 Codex 不可写稿/发布。
6. 本机缓存解析与迁移工具：分离可重建索引和业务台账，增加 dry-run、恢复日志、旧布局只读兼容及一次切换。已配置新资料库的工作区不允许隐式回退旧布局。
7. 上述约定、文档与测试同批更新；隔离夹具验收后生成真实项目 dry-run。待真实归属/迁移清单明确且获授权，再分批执行和验收。

本轮不包含改写视频内容、生成新封面/视频、购买额度、自动发布、重做宿主调度系统或开放跨机器网络服务。

## 12. 边界清单与验收

| 边界 | 处理方式 | 必须验证的结果 |
| --- | --- | --- |
| 活动资料库目录被删、只读或 NAS 活动库断连 | 阻断生产写入，返回位置与原因，保留可恢复请求 | 程序目录、旧 broll、默认本机根均无新业务文件；不中途重建一个“同名 NAS 目录” |
| 开写即建项目 | pack 前置建立，其他首次写稿入口兜底，绑定幂等 | 两宿主、重试、重领包、改标题仍只得到同一目录 |
| 单套目录与状态来源 | 一个活动绑定、项目内权威记录、只读导出 | 人工改项目信息/旧 workflow-state 不改变状态；旧 contents 不继续接收业务写入 |
| 进行中项目迁移 | 停写、清单、校验、恢复日志、专用代次迁移 | 写作包继续提交；等待 A-roll 后可 handoff；正在剪辑可从原时间线/任务继续并在批准后 register |
| 不可变交接与定稿 | 旧包原字节保留；v2 冻结稿和出处，身份不依赖挂载绝对路径 | 定稿哈希一致；变更出处/拍板信息使新代次变化；旧代迟到登记被拒 |
| 原文证据缺项 | 明确缺失/来源等级，写稿侧补齐 | 数字/归因引述定位可追溯；不凭台账存在宣称已逐句核查；不编原话、URL |
| 素材绝对路径 | 分类型复制或重定位，磁盘保存相对路径 | 移动挂载点后仍可读；缺失、无权限、多候选明确显示且阻止依赖操作 |
| 两机访问 | 单写服务+执行机器认领+写前复核，异常不自动抢锁 | 第二写者被拒；断连旧进程恢复不能继续写；只读查看不取得发布/审批权 |
| 纯图文稿 | 建项目，视频目录懒创建，不要求 A-roll | 写稿、配图、发布和回流完整可用；handoff 仍拒绝非视频平台 |
| NAS 普通文件、本机数据库 | 分开解析与扫描，保留不能丢的业务记录 | 新受管目录不落检索数据库/WAL；删除本机派生索引可重建；内容与台账仍在 |
| 失败/断电/磁盘满 | 任一提交点可恢复，未切换不改原件 | 无半个生效绑定、双正本、重复版本/重复登记；真实源变动触发停止 |
| 外部工程依赖 | 软件支持的重连，保留同一个工程与匹配字幕 | 实际打开原时间线、定位媒体并验证可继续；单纯哈希成功不算编辑恢复成功 |
| 约定一致 | 三处目标、真实技能源及新项目入口一起更新 | 新会话使用绑定的本地新项目，完成后按验证流程归档 NAS；项目外旧路径只出现在有标注的历史记录 |

验证分层：有意义的存储/事务/路径/权限回归测试，类型检查与构建；隔离项目上完成 pack → 多版稿件/证据 → handoff → report → 批准记录 → register → 发布包/回执只读核对；真实迁移完成字节、编号、版本和恢复检查。真实发表、付费生成和模型事实判断质量不属于这些测试的自动通过项。

**Jev 可作为恢复验收样例，但当前不能当作 register 成功样例**：它的内容归属尚未确认，gate4 仍 pending。验收不得伪造绑定、审批或发布结果来凑完整流程。

## 13. 审核后下一步

创始人已确认本地新库与当前稿接续范围。只对当前稿及必要设置生成逐文件清单、校验后切换服务；旧项目和整库迁移取消，不继续请求 Jev 等归属信息。完成后报告实际活动路径、当前稿版本/写作包保持结果及服务状态。

本 spec 的完成标准是设计可审阅、迁移与边界明确，不代表以上尚未实现能力已经上线。
