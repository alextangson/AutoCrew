# 总编辑对话接本机 agent（Claude / Codex / WorkBuddy）— spec v3

> 2026-09-28。v1→v2 创始人答 Q1–Q4；v2→v3 吸收 Codex 评审（原文在文末）。
> 创始人定调：**A 的信任模型 + B 的节奏**，最终支持 Claude、Codex、WorkBuddy 三家。

## 目标

网页总编辑输入框加「后端」切换：本机 Claude / 本机 Codex / 本机 WorkBuddy / 内置引擎（备用，只在手动切换时用，永不自动降级）。
选本机时，消息交给本机 agent，它通过 `:4317/mcp` 调 AutoCrew 工具，结果以卡片回到对话里。

## 信任模型（A）——写在明处

本机 agent = 创始人在自己电脑上开的 Claude Code 同等权限：能读写文件、跑 shell。
**AutoCrew 的软门禁拦不住它**（shell 能直接改库文件、读令牌）。我们防的是**误操作**（危险动作先确认、发布前审批），
不防被网页/资料里的恶意指令诱导。设置页和首次使用时明说这一点。

## 接法：ACP（三家已核）

| 后端 | 启动方式 | 核实依据 |
|---|---|---|
| Claude | `@agentclientprotocol/claude-agent-acp`（npm 0.81.x） | ChatCut 数据目录里 `acp-agents/provider-config/claude-acp` |
| Codex | `@zed-industries/codex-acp`（npm 0.16.x） | ChatCut 同目录 `codex-acp` |
| WorkBuddy | App 自带 CLI `…/WorkBuddy.app/…/cli/bin/codebuddy --acp` | `--help` 里原生 `--acp`（stdio ndJson） |

版本锁死。守护进程是 ACP client，三家共用一套：initialize → session/new（带 mcpServers、cwd）→ prompt → 流式 update / tool_call / request_permission → cancel → session/load。

## 节奏（B）

- **阶段 0 spike（每家单独过）**：真实危险工具会发 request_permission、允许/拒绝都生效、cancel 生效、进程重启后 session/load 能续、MCP http 带鉴权头能连上、认证失败的报错长什么样。哪家不过，哪家不上，回来报告。
- **阶段 1：Claude 端到端**，把下面的地基全做完。
- **阶段 2：接 Codex、WorkBuddy**——地基复用，每家只是启动命令 + 差异适配 + 过 spike。
- **v2（不在本期）**：模型选择器、完整卡片映射、多 agent 并发。

## 地基设计（对应 Codex P1/P2）

1. **令牌与权限（P1-1）**：前置依赖——命名宿主令牌禁止访问 `/api/*`（另一个会话在修）。
   每个 agent 会话签发一枚**会话级 MCP 令牌**，服务端记 {后端, 资料库, 对话 id}；只认 `/mcp`，会话结束即撤销。
2. **执行前审批（P1-2）**：发布类动作（各平台发布、转入已发布、删除类）由 agent 会话调用时，MCP 层不执行，
   回 `approval_required{approval_id, next_action}`；网页弹审批卡（展示动作/目标/内容摘要）；
   审批绑定 动作+目标+内容指纹，单次消费、有期限；批准后系统自动给 agent 发一句「已批准 approval_id=…，继续」，agent 带 id 重调。
   复用现有 approval 服务（`APPROVALS.issue/consume`）与 codex handoff 的 confirmation_id 模式。
3. **shell / 文件权限（P1-3）**：ACP request_permission → 网页权限卡：允许一次 / 拒绝。**v1 不做「本对话都允许」**。
   人设要求写稿审稿发布走 MCP，但如信任模型所述，这只是约定。
4. **归属（P1-4）**：结果归属靠会话令牌（不靠自报请求头）。每次 MCP 调用**进入时**就打上 {对话, 轮次, 调用 id}；
   这时没有进行中的轮次 → 记为「后台结果」追加到对话，不塞进下一轮。卡片按调用 id 去重、先落盘再推送。
5. **资料库固定（P1-5）**：会话创建时绑定资料库；切库不影响正在跑的 agent，它的调用仍落在原库。
6. **对话锁（P1-6）**：本机后端强制带 turn_id/client_id；服务端按 资料库+对话 加锁，整个执行周期（含等审批）只有一轮。v1 全局同时只跑 1 个 agent。
7. **持久化与恢复（P1-7）**：启动 agent 前先落盘 对话/后端/ACP session/轮次/资料库；轮次状态 running / awaiting_approval / done / interrupted。
   守护进程启动时把残留 running 标成 interrupted。**绝不自动重放**结果不明的写操作。
8. **进程收尾（P2-9）**：先 ACP cancel，5 秒后杀整个进程组（detached 启动）；记录 pid+命令，启动时清理孤儿。
9. **刷新恢复（P2-10）**：回到页面重新挂上进行中的轮次（停止按钮可用），待处理的审批/权限卡可查询重放；多标签页只有一个能应答（单次消费）。
10. **认领（P2-11）**：等审批超过 10 分钟可能丢认领 → 批准后重验；claim_held 如实转述。claim_token 永不进卡片/日志/SSE。
11. **后台回流（P2-12）**：本机后端的对话，调研完成等回流只追加结果卡，不自动启动模型轮。
12. **工作目录与人设（P2-13）**：cwd 固定 `~/.autocrew/chief-editor/`（人设在此，三家各自的 CLAUDE.md / AGENTS.md / CODEBUDDY.md）；对话的后端以服务端记录为准，localStorage 只作新对话默认值。
13. **脱敏（P2-14）**：卡片字段白名单；错误先脱敏再截断。
14. **就绪状态（P3-15）**：切换器分别显示「没装 / 未登录 / 可用」；Claude/Codex 标「用你的订阅」，WorkBuddy 标「用 WorkBuddy 额度」，不笼统承诺走订阅。

## v1 卡片

稿件结果卡（打开稿件）、任务状态、执行前审批卡、权限卡；其余工具结果显示成脱敏的简短文字。完整卡片映射放 v2。

## 边界清单（验收时逐条过）

| # | 场景 | 行为 |
|---|---|---|
| 1 | 没装 / 没登录 / 额度用完 | 切换器标明状态；发送后报错气泡给原因+修法；绝不自动走内置引擎 |
| 2 | 点停止 | ACP cancel → 5 秒后杀进程组；气泡列出停之前已完成的写动作 |
| 3 | 同对话多标签页同时发 | 第二个被拒：「这段对话正在跑」 |
| 4 | 已有 1 个 agent 在跑，再开别的对话发 | 明说「已有一个本机 agent 在跑」，不排队 |
| 5 | 刷新 / 断线 | agent 继续跑；回来恢复进度、停止按钮、待处理卡片 |
| 6 | 守护进程重启 | 残留轮次标中断，进程组被清掉；可重发（session 能续就续，续不上说一句「已新开」） |
| 7 | 审批 / 权限卡没人理 | 挂着等；10 分钟没应答按拒绝，告诉 agent |
| 8 | 审批后稿件又被改过 | 指纹不符，审批失效，要求重新确认 |
| 9 | 切资料库时 agent 在跑 | agent 继续写原库；切换器提示「后台 agent 仍在处理旧库」 |
| 10 | 认领被别的会话占着 / 等待中被接管 | 如实转述是谁占着；不绕过 |
| 11 | 调用迟到（停止后才返回） | 记为后台结果追加到对话，不串到下一轮 |
| 12 | ACP 输出解析失败 / 适配器崩溃 | 该轮报错并附脱敏后的最后几行，不吞 |
| 13 | 对话中途换后端 | 新开一段对话，旧的保留 |
| 14 | 内置引擎没配置 | 备用项置灰；本机后端不受影响 |

## 不做（本期）

模型选择器、完整卡片映射、多 agent 并发、「本对话都允许」、自动降级到内置引擎、删除内置引擎。

## Codex 评审原文（2026-09-28，consult，未改动）

**结论：这版不能直接开建。阻塞项是权限隔离、执行前确认、轮次归属和恢复契约；ACP 本身解决不了这些问题。**

以下基于已核对的源码。两个 ACP 适配器的具体版本实现未验证，因此不能把权限、续会话、模型列表和 HTTP headers 写成已具备能力。

**P1｜开建前必须修**

1. **命名宿主 token 可以绕过 MCP 权限进入 IPC。**  
   `AUTH.identify` 接受命名 token，但 `/api/invoke` 只保留认证方式、不检查主体；Bearer 还跳过 Origin 校验。受限宿主因此能直接调用聊天入口，新增后可间接启动全权限 agent。  
   证据：`src/desktop/server-auth.ts:84–95`、`desktop/server.ts:99–107,374–397`。  
   **改法：**IPC 保留主体并实施通道授权；agent token 仅能访问指定 MCP 工具，不能启动 agent、签发批准或消费网页批准。

2. **“发布类 MCP 已有确认卡”不成立。**  
   内置聊天的确认卡在执行前生成；MCP 则直接执行工具。`wechat_mp_draft` 工具最终直接调用发布实现，没有消费网页审批凭证。“执行完翻译卡片”已经太晚。  
   证据：`src/desktop/chat-router.ts:1349–1368`、`mcp/server.ts:179–199`、`src/tools/publish.ts:234–263`；真正的审批消费在 `src/desktop/ipc.ts:488–517`。  
   **改法：**将批准检查放到所有入口共用的执行边界，绑定动作、目标和内容版本；确认卡只负责展示待批准请求。

3. **全权限 shell 与“不绕过稿件门禁”互相矛盾。**  
   人设不能阻止 shell 改库文件、读其他宿主 token、调用 IPC。检查 `rm` 也无法覆盖 Python 删除、重定向覆盖、脚本及子进程。提示注入一旦触发已放行工具，就获得同样能力。  
   证据：`src/desktop/host-cli.ts:93–113` 只写提示文件；`src/desktop/host-tokens.ts:65–74` 使用同用户文件权限；`mcp/host-policy.ts:54–61` 仅管 MCP 调用。  
   **改法：**选择真实隔离边界：只开放渲染输出目录、隔离凭证和业务库写权限。做不到就明确这是可信本机全权限执行，不能承诺强制门禁。v1 删除“本对话所有 shell 都允许”。

4. **固定 conversation header 不能可靠绑定“当前轮”。**  
   A 轮请求迟到、停止后返回、后台任务完成时，当前轮可能已经是 B。两个会话共用宿主 token，也不能靠自报 header 证明归属。现有 session header 明确只作诊断。  
   证据：`desktop/server.ts:247–255`、`mcp/access.ts:24–34`、`mcp/server.ts:173–177`。  
   **改法：**服务端签发绑定 workspace/conversation/session 的执行凭证；每次工具调用进入时固定 turn/run/call 归属，完成时不能重新找“当前轮”。旧进程凭证撤销，结果按调用 ID 去重、持久化。

5. **MCP 还可能跨资料库执行。**  
   `/mcp` 每次请求重新取当前活动资料库；聊天 IPC 则在入口解析资料库。长轮次中切库，后续 MCP 调用可能落到另一库。conversation header 不解决这个问题。  
   证据：`desktop/server.ts:246–255,390–395`。  
   **改法：**会话创建时固定 workspace，MCP 从可信会话绑定解析；切库不得改变正在执行的 agent 目标。

6. **registerTurn 并不保证同一对话单轮执行。**  
   它只拒绝重复 turn ID 和同 `client_id`；不同标签页能同时跑同一 conversation。持久化队列只串行写盘，两轮仍读到相同旧历史。  
   证据：`src/desktop/turn-registry.ts:53–75`、`src/desktop/chat-persist.ts:9–12,98–117`；登记字段目前可省略：`src/desktop/ipc.ts:602–615`。  
   **改法：**本机后端强制登记，以 workspace+conversation 锁住整个执行周期；三个进程的配额也必须服务端原子分配。

7. **现有恢复机制不能兑现“崩溃后结果落盘、可续”。**  
   首轮成功后才创建会话；活跃轮仅在内存，settle 才写完成索引。重启时只能查到 `unknown`，没有“中断”记录。并发 settle 的索引读改写还可能互相覆盖。  
   证据：`src/desktop/chat-persist.ts:149–154`、`src/desktop/turn-registry.ts:43,114–149`。  
   **改法：**启动 agent 前持久化 conversation、backend、session、turn 和 workspace；记录运行、待批准、完成、中断状态。卡片与副作用回执先落盘再推送。重发不得自动重放结果不明的写操作。

8. **ACP 选型依据尚未成立，spike 验收过弱。**  
   `initialize→new→prompt→load` 不能证明实际危险工具都请求批准，也不能证明重启后 load、headers 重建、模型切换及批准取消正确。方案第 5 条又混入直接 CLI 的 resume 参数，混淆两条实现路线。  
   证据：方案 §1/§5；当前入口仍固定调用内置运行链：`src/desktop/ipc.ts:633`、`src/desktop/chat-persist.ts:95`。  
   **改法：**锁定适配器版本，先验证真实工具的允许/拒绝、取消、进程重启后续会话、HTTP 鉴权及自定义头、模型发现/设置、认证方式。**需要网页交互批准时，ACP 比单纯 JSON 输出更匹配；只需流式和续聊时，直接 CLI 更简单。不能仅凭协议名称断定适配器满足要求。**

**P2｜应该修**

9. **进程组不会因父进程退出自动全部结束。**  
   SIGTERM adapter 不保证终止它的 shell/ffmpeg；父进程崩溃也不会可靠运行清理钩子。当前关闭钩子只处理已有服务。  
   证据：`desktop/server.ts:445–457`、`src/desktop/ipc.ts:722–727`。  
   **改法：**先协议取消，再限时终止所拥有的进程组；记录进程身份并设计启动时孤儿处理。区分 daemon 管理的后台任务与 agent 子进程，不能全杀或全保留。

10. **刷新恢复不等于恢复停止按钮和权限请求。**  
    当前恢复路径主要轮询完成后加载会话；停止按钮依赖 `turnIdRef`。没有待批准请求的查询、重放、过期及多标签页抢答契约。  
    证据：`frontend/src/chat/ChatDock.tsx:235–258,383–388`。  
    **改法：**恢复时重新附着运行轮；批准请求具有服务端 ID、期限和单次消费状态，并绑定具体参数。停止、超时和进程退出必须使批准失效。

11. **claim_token 不是会话锁，“等用户回答”可能丢认领。**  
    普通租约 30 分钟，同宿主 10 分钟未写入即可 takeover；持有正确 token 可通过写门，`local-user` 另有覆盖权。因此“后来者永远 claim_held”只覆盖部分路径。  
    证据：`src/storage/claims.ts:35–43,131–136,244–259`。  
    **改法：**规定 token 的安全保存、续租、释放和接管行为；批准等待后重新验证认领。禁止通用卡、日志和 SSE 泄漏 token；旧 session 恢复后不能盲用旧认领。

12. **“绑定后端”漏掉后台回流入口。**  
    调研完成仍直接调用 `runPersistedChatTurn`，默认走内置引擎；这会违反“只手动切换才用内置引擎”。  
    证据：`src/desktop/chat-followup.ts:211–217`、`src/desktop/chat-persist.ts:95`。  
    **改法：**所有入口统一按持久化后端路由；v1 可只追加确定性的任务结果卡，不自动启动模型回流。

13. **工作目录和人设规则冲突。**  
    人设放在 `chief-editor`，实际 cwd 却可能是内容项目；计划没有说明如何保证人设加载，也未规定 resume 时 cwd 是否可变。`writeHostPersona` 还只接受现有宿主类型。  
    证据：`src/desktop/host-cli.ts:20–35,93–113`。  
    **改法：**分离认证主体与 adapter 类型；固定 session cwd，通过已验证的机制注入人设，不依赖另一个目录的文件。已有会话后端以服务端记录为准，localStorage 仅作新会话默认值。

14. **“原始错误尾部”和通用卡会泄漏敏感结果。**  
    MCP 返回完整 `structuredContent`，其中可能有认领凭证；现有 SSE 向全部已连接客户端广播。直接展示关键字段或 stderr 尾部没有脱敏保证。  
    证据：`mcp/server.ts:195–199`、`desktop/server.ts:84–90`、`src/tools/desk.ts:190`。  
    **改法：**卡片采用字段白名单，错误先脱敏再截断；凭证只保留在执行上下文，不进入展示事件。

**P3｜可后补**

15. **模型与安装状态的 UI 承诺过细。**  
    找到 CLI 不等于 adapter 可运行、已认证或确实使用订阅；模型列表也不证明账户可用。  
    证据：现有模型入口仅反映内置引擎配置：`src/desktop/ipc.ts:735–743`。  
    **改法：**分别报告 adapter 就绪、认证状态和模型能力；v1 使用已验证默认模型。不要承诺所有调用都走订阅额度，尤其 MCP 工具仍可能调用内部 API。

**v1 该砍掉什么**

- **砍双后端同时上线**：先做一个通过上述 spike 的后端。
- **砍全权限 shell 和整段对话通配批准**：先限制到业务 MCP 与受控渲染目录。
- **砍完整卡片映射**：只做稿件结果、任务状态、执行前确认，其余脱敏文本。
- **砍三个并发 agent**：先全局一个，保留按对话锁。
- **砍模型选择器**：先 CLI/adapter 默认模型。
- **砍丢 session 自动新建并继续执行**：标记断开，保留历史，避免重放副作用。
- **砍自动模型回流**：后台完成只追加结果通知。
- **不能砍**：IPC 主体授权、执行前批准、可信轮次归属、持久化恢复和子进程收尾。
