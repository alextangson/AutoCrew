# 用户资料库与本机配置

AutoCrew 程序目录只保存代码、通用模板、技能和软件开发文档。运营资料从创建开始进入用户指定的资料库。活动资料库可放本地或 NAS；完成项目按用户约定归档，不能把归档副本与活动正本同时作为可编辑来源。

当前用户于 2026-09-26 改为本地工作、完成后 NAS 归档：本地资料库 `~/AutoCrew资料库`（2026-09-27 从 `~/Documents` 迁出：那里开着 iCloud「桌面与文稿」同步，GB 级原片会上传且可能被换成只在云端的占位；旧路径留有指向新位置的符号链接，供剪映工程和旧会话里的绝对路径继续解析），本机配置 `~/.autocrew`，NAS 归档根 `/Volumes/<NAS 卷>/<账号>/Account/YYYY/<EnglishMonth>/`。本次新建独立编号的本地资料库，只接续正在写的 `content-1790393879117-j2v9ag` 及该稿选题、采用的调研与写作包；保留其内容编号、版本、认领和进度，并沿用本机连接配置。历史稿件、回收站和四组旧视频保持原位，不执行整库迁回，也不要求旧视频归属确认。本地新库从启用开始使用共享项目 v2。

## 旧资料库目录（历史资料保持原位）

```text
用户选择的资料库/
  autocrew-library.json             资料库版本与稳定编号
  workspaces.json                   运营主体名称、编号与当前选择
  shared-assets/                    跨运营主体的通用素材
  workspaces/
    default/                        默认运营主体
      creator-profile.json          定位、受众、写作要求
      topics/                       选题与来源
      contents/<稳定内容编号>/      元数据、稿件、版本、项目素材、发布结果
      library/                      常备素材索引与受管文件
      research/                     调研资料和来源证据
      projects/                     新的视频制作工程默认位置
      reports/                      运营复盘
      imports/                      待关联到具体内容的历史制作资料
    ws-.../                         其他独立运营主体，同样结构
```

保留现有内容编号、状态机、topicId/siblings 多平台关联和稿件版本。每个项目在选题、写作、剪辑、发布、复盘期间保持原目录。年份归档等原有 NAS 目录可以与以上目录共存，不会被覆盖或自动改名。

本机根目录仍为 `~/.autocrew`；`AUTOCREW_LOCAL_DIR` 可覆盖。未配置资料库时保留旧版兼容行为，`AUTOCREW_DATA_DIR` 仍可用于隔离开发/测试。新资料库通过本机 `storage.json` 定位：

- `libraries/<资料库编号>/workspaces/<主体编号>/`：模型、发布、搜索、封面和视频连接配置。密钥文件权限 0600。
- 根目录 `inbox.json`、`tokens/`、`server-token`、服务进程记录与 `server.log`：本机私有运行和连接数据。
- `migrations/`：迁移校验清单与旧位置。文件清单不包含凭据内容。
- 平台 Cookie 继续由独立发布环境管理；资料库中的账号信息不等于登录凭据。

结构化素材索引在新资料库中使用工作区相对路径。新导入的外部素材先复制、校验，再登记；原文件保留。稿件附件仍保留采用版本的快照。历史制作工程中由其他软件管理的引用应通过该软件重定位，不直接重写其私有项目格式。

## 用户操作

设置页顶部的“用户资料库”提供新建、打开、迁移、位置检查和取消待切换。保存位置仅准备操作，重启时停写后执行。也可使用：

```bash
autocrew storage status
autocrew storage preview /完整/目标路径
autocrew storage migrate /完整/目标路径
autocrew restart
```

`create` 建空资料库；`open` 打开已有资料库；`migrate` 搬迁现有 AutoCrew 资料。操作不会自动删除源资料。已有目录可以包含其他项目，但不得有冲突的 `workspaces`、`shared-assets` 或资料库标记。

迁移先写独立暂存目录，逐文件比较 SHA-256；源数据清单或校验值变化就停止。内容中的内部绝对路径随迁移更新，素材库外部文件纳入受管目录。已知凭据只复制到本机私有配置目录；未分类文件留在原处并进入报告。所有校验通过后才写资料库标记与本机位置指针。失败的暂存目录保留供恢复，不能直接当成已完成资料库。

切换前后的本机 `storage.json` 位置和迁移报告一起提供恢复依据。回到迁移前数据会丢失切换后的新增工作，因此回退前必须先停止服务并保留当前资料库；不能将旧备份当成最新正本。

## NAS 与并发边界

- 程序运行在本机；当前用户的活动资料也在本地，NAS 未连接不阻止本地制作。选择 NAS 作为活动资料库的其他用户仍在断连、只读或身份不匹配时明确报错，不自动新建第二套数据。
- 一个资料库同时只允许一个 AutoCrew 守护服务。其他宿主通过该服务的 MCP 入口访问；不启动第二套直接写同一资料库的进程。
- `.autocrew-writer` 是占用记录。正常退出自动释放；异常退出后先确认占用机器上服务已停止，再处理残留记录。不会自动抢占其他机器。
- 正常释放先将自己的完整占用目录移开，再清理已释放记录；避免 SMB 重启期间读到半清理的空占用目录。已被替换的占用不得删除当前写者记录。
- 日常编辑缓存可由剪辑软件保留在本机；原始素材、编辑工程和最终交付件属于资料库。NAS 本身仍需备份。

完成视频按 video-project-lifecycle 做 NAS 归档：保存已批准版本、字幕、可编辑工程及依赖，逐文件比较并验证可恢复。清理只针对已明确归属且恢复验证通过的文件，保留本机运营记录与归档位置；受管项目尚不支持的归档引用先保留本地文件。改变存储政策本身不会批量归档或删除现有四组旧视频。

## 开发与内容生产约定

业务数据使用 `getDataDir()`；本机连接配置使用 `getConfigDir()`；服务令牌使用 `getHostStateDir()`。不能把数据目录、配置目录和程序安装目录当成同一个路径。

外部 Agent 开始内容生产前读取 `autocrew storage status`，通过工具取得当前主体和内容编号。研究、封面、素材和剪辑产物写入该主体对应目录，不再写进程序的 `docs/research`、`output` 或 `tmp`。通用程序文档、测试夹具和模板仍保留在代码仓库。

本次验证针对确定性的存储、迁移和设置界面；没有评估模型是否始终遵守以上内容生产约定。

## 共享内容项目 v2（2026-09-26）

新建资料库/工作区使用 `project-layout.json` 与 `project-registry.json`。已有资料库须经过共享项目迁移，不能仅改路径配置。上文 `contents/<id>` 是未迁移的旧布局，v2 只读写 `projects/YYYYMMDD 初始标题--完整content_id/`。

项目从开写时存在；`00-project/autocrew` 保存权威业务记录，`01-script` 保存采用的研究、来源、出处、文稿版本和不可变交接，02–07 沿用剪辑分类。保留 `05-audio` 与 `05-cover`。纯图文也建项目，视频目录按需建立。`contentFile/contentRoot` 是内容路径唯一入口，不在各模块拼接旧目录。

项目 AGENTS.md、项目信息、导航、workflow-state 为生成视图。改稿通过 AutoCrew，执行事实通过受限 report；人工批准来自工作台，register 核对服务批准记录。v2 清单不含机器挂载绝对路径，定稿原字节冻结，旧包不原地改写。

迁移工具（本机 CLI，正式服务必须停写才能 apply）：

```bash
npx tsx scripts/projects.mts plan <工作区完整路径> <本机预览.json> [旧项目扫描根…]
npx tsx scripts/projects.mts apply <已确认清单.json>
npx tsx scripts/projects.mts resume <同一清单.json>
npx tsx scripts/projects.mts verify <同一清单.json>
npx tsx scripts/projects.mts rollback <同一清单.json>
```

plan 只读扫描并生成逐文件哈希、归属、状态及依赖清单。apply 遇到未确定归属、缺失依赖或无法核实的旧交接/审批就拒绝；不会按标题猜测。有效旧交接必须满足原文、A-roll、决定与出处条件，迁移后以 g+1/v2 替代并撤销旧凭据。编辑器实际打开恢复与文件哈希验证分别验收。

程序保留迁移日志和原件恢复隔离区；不会自动删除原件。仅没有新增工作时才可回退，新增内容触发停止并要求保留新增工作的恢复方案。索引、代理和软件数据库位于本机 cache；JSONL 来源台账属于业务资料。资料库写入占用每次提交复核 nonce，第二台执行机器不能自动接管；本机服务不会为此开放远程网络。

迁移与回退期间，工作区的 `.project-migration-active.json` 阻止服务读取半套布局。中断后使用同一清单执行 `resume`；已经开始回退则重试 `rollback`，每个移动步骤都依据原日志恢复。首次建稿先保留内容编号和完整初稿的创建记录，再公开绑定；中断后列表恢复同一条内容。普通更新捕获到写入失败时取消未提交事务；无法确定提交结果则保留日志并报“待恢复”，不谎报回滚成功。

## SMB 的不可变版本写入

简报和视频版本共用 `writeJsonOnce`：通过服务器支持的独占目录创建锁住目标版本，检查目标不存在，把完整临时文件一次 rename 到正式文件。所有受管发布者遵循同一协议，并发只有一个成功；已存在的版本不会被覆盖。读者不会看到半份 JSON，不依赖 SMB 不支持的硬链接。素材挂接保留本机硬链接节省空间的行为，在 EXDEV、ENOTSUP 等错误时复制；允许覆盖的素材更新与不可变版本是两种既有契约。

若进程或连接在发布过程中异常中断，可能保留 `<版本文件>.publish-lock`，其中有 owner 和临时内容。服务明确报错，不按时间或远端 PID 自动抢占。先确认原写入者已经停止并核验正式文件和暂存内容，才能处理残留；不能把“重试”当成覆盖原版本的许可。

## 我的内容：创始人看的视图（2026-09-27）

AI 的项目目录（`workspaces/default/projects/…`）原地不动，发布计划、剪映工程、登记校验都记着它的绝对路径。人看的是资料库根下另建的 `我的内容/`，由守护进程启动时和之后每 60 秒对账生成；其余根目录条目在 Finder 里设为隐藏（`chflags hidden`，⌘⇧. 可见）。只做 default 工作区。

栏目文件夹名带阿拉伯数字前缀，Finder 按流程排序：`1 写稿中`、`2 待录制`、`3 剪辑中`、`4 待发布`、`5 已发布`、`6 复盘`（中文数字在 Finder 里按拼音排，不用）。代码里的栏目键仍是不带数字的名字，显示名只在 `my-content-plan.ts` 的 `columnDir` 一处映射。旧版无编号的栏目目录在清单里记为 `_column`，下一轮对账按原有规则清理：空的删掉，里面有创始人文件的原样保留。

| 栏目 | 稿件状态 | 放什么 |
|---|---|---|
| 1 写稿中 | drafting / needs_evidence / reviewing / revision（有稿才出现） | 口播稿.md |
| 2 待录制 | 视频平台的 draft_ready / approved | 口播稿.md |
| 3 剪辑中 | editing / cover_pending | 口播稿.md、`成片放这里/`（指向项目 `07-delivery/export/` 的链接，剪映直接导出进去） |
| 4 待发布 | publish_ready / publishing；非视频平台的 draft_ready / approved 也在这 | 成片.mp4、封面-3x4、封面-4x3、口播稿.md、发布文案.md；登记过成片的加 口播稿-实拍版.md 和（有新增时）发布前核对.txt；缺的写进 `还缺什么.txt`，不编造 |
| 5 已发布 | published，按发布时间只留最近 5 条 | 同待发布 |
| 6 复盘 | — | 最新复盘.md |

规则：
- 文件夹名 `MMDD 标题`，去掉［生成中］前缀和文件名非法字符，截 40 字，重名补稿件 ID 尾号。换栏目、改标题时跟着挪或改名。
- 成片、封面用硬链接，拖去上传不占双份；硬链接失败（跨盘、SMB）退成符号链接。
- 稿子是只读副本，AI 改稿后下一轮对账更新。写稿中、待录制的口播稿改了会写回稿件（见下一节）；其它栏目或写回不了的，改过的副本另存成「口播稿（我改过的 时间）.md」保留，不覆盖。
- 清单 `我的内容/.autocrew-view.json` 记着对账放进去的每个条目；只删清单里且仍是原样的条目，创始人自己放的文件永不删，有外来文件的文件夹原样保留。
- 对账出错写 `我的内容/⚠️ 同步出错.txt`，单条出错不挡其它条，下一次全成功时删掉。这个文件和 NAS 归档共用：各自的问题分栏存在隐藏的 `.autocrew-errors.json`，谁跑谁只替换自己那一栏（`my-content-errors.ts`），两栏都空才删。
- 不做：多工作区、从文件夹自动收口播原片、写稿中 / 待录制以外栏目的改动同步回 AutoCrew。

### 创始人改稿回流与实拍版（2026-09-27）

录之前，创始人改的字回到稿件；录之后，实际说出口的话从成片字幕回到 AutoCrew。两头都记成改稿差异（`learnings/edits`），写手经 `recentContrastPairs` 学到创始人的说法。

**录之前：改稿回流**（`src/storage/my-content-sync-back.ts`，对账第一步、生成清单之前）
- 扫清单里 `1 写稿中` / `2 待录制` 下的 `口播稿.md`：内容哈希 ≠ 清单记的哈希 = 创始人改过。
- 能写回时走与 content update 同一个 `updateContent` 通道存成新版本（版本备注「创始人在「我的内容」里改稿」），并 `recordDiff`（before = 当前正文，after = 创始人全文，带平台）。同一轮对账生成的新副本就是这份改稿，文件原地收下、恢复只读，不出「我改过的」副本；下一轮哈希一致，不再动。
- 不写回（文件挪成「口播稿（我改过的 时间）.md」，原因写进 `⚠️ 同步出错.txt`，不记差异）：
  - 这篇有非 local-user 的活认领（`claims.ts` 的 `activeClaim`），或写作包 `state=preparing`（`writer-pack.ts` 的 `readPack`）——AI 正在写；
  - 改后文件为空或只有空白——按误操作；
  - 对账时稿件已不在写稿中 / 待录制（交剪辑后定稿锁定）；改稿留在旧文件夹，新栏目放原稿；
  - 创始人改的同时 AI 也更新了稿子（当前稿哈希 ≠ 清单哈希）——不覆盖 AI 的新版本。

**录之后：实拍版**（`src/modules/video/handoff/spoken.ts`、`register-spoken.ts`）
- 视频平台稿件的 `autocrew_video register` 必须带 `srt_path`（成片最终版字幕，在项目目录里）；缺了回 `invalid_params`（which=srt_path），格式不对回 `srt_invalid`，都在任何落盘之前，不静默跳过。
- 字幕还原：去序号和时间轴、拼句（中文直接拼，西文补空格），相邻两条间隔 ≥ 1.5 秒换段。登记成功后存 `01-script/spoken/gNNNN-spoken.md`，并记差异（before = 该代次 `final-script.md`，缺则稿件正文；after = 实拍口播；备注「实拍口播与定稿的差异」）。重放直接返回、不重复记；同代次再登记且口播文本相同也不重复记。登记已提交后实拍版才落盘，这一步失败不回滚登记，而是在回执里带 `warning`。
- 视图：`4 待发布` / `5 已发布` 有实拍版时放 `口播稿-实拍版.md`（只读副本）。实拍版里出现、定稿里没有的数字（阿拉伯数字，可带 % / 万 / 亿；中文数字 + 万 / 亿；百分之…）和出处说法（含「据」「报告」「说」的分句且不在定稿里）列进 `发布前核对.txt`，只提醒不挡发布；没有新增时不出现。

### NAS 归档（2026-09-27）

发布过的视频素材占本机空间，但口播稿、发布记录还要留着给复盘和写手学。所以每天把老稿件整个项目复制到 NAS，核对无误后只删本机的素材目录。实现：`src/storage/nas-archive.ts`（编排）、`nas-archive-copy.ts`（复制与校验）、`nas-archive-log.ts`（台账和归档记录.md）。

**哪些稿件归档**（全部满足）：`status = published`；有 `publishedAt` 且已满 7 天；不在按 `publishedAt` 排的最近 5 条已发布里（与「5 已发布」栏共用 `KEEP_PUBLISHED`）；没有活认领（`activeClaim`）；还没归档过（有 `00-project/notes/archive-*.json` 且素材目录都空）。

**每条怎么做**
1. 目标：`<归档根>/<年>/<英文月份>/<项目文件夹名>`，年月取 `publishedAt`（本机时区），如 `…/2026/September/20260901 标题--content-…`。归档根默认 `/Volumes/<NAS 卷>/<账号>/Account`，目前没有现成配置项，只能由调用方 `archiveRoot` 选项改（测试用）。
2. 归档根不存在（NAS 没挂载）：一条都不动，`⚠️ 同步出错.txt` 写「NAS 未连接，有 N 条待归档」；挂上后下一轮成功即消失。
3. 目标卷剩余空间（`statfs`）< 项目大小 + 1 GB 预留：这条跳过，原因写进出错文件。
4. 整个项目目录逐文件用普通 `copyFile` 复制，不用硬链接、不做 rename 落位（见「SMB 的不可变版本写入」）。目标已有的文件先算 sha256，一致就跳过，不一致就删了重拷——中断后续跑安全。
5. 每个文件复制后再算 NAS 上的 sha256 和本机比。任何一个文件出错或不一致：本机一个都不删，报错，下一轮重试。要删的目录里有符号链接等非普通文件也按出错处理。
6. 全部核对通过后：先写 `00-project/notes/archive-<时间>.json`（目标路径、每个文件的相对路径 + sha256 + 大小、删了哪些目录、时间），再把被删目录下每个文件的 `@project/<相对路径>` → NAS 绝对路径合并进 `00-project/autocrew/relocations.json`（`portableProjectRecord` 解码时据此指到 NAS）；只为真正要删的文件写重定位。
7. 然后删 `02-aroll`、`03-broll`、`04-edit`、`05-audio`、`05-cover`、`07-delivery` 并重建为空目录，项目骨架不变；保留 `00-project`、`01-script`、`06-publish`、根目录 md、`.autocrew-owner`。
8. 删到一半失败：记录已在，素材目录不空 → 下一轮不算「已归档」，重新复制核对剩下的文件后补删，重定位只增不减。

**看得见**：工作区 `archive-log.json` 是台账（同一稿件续跑补删的空间累加到同一行）；「我的内容」清单里多一个受管只读副本 `归档记录.md`（最新在前：归档日期、标题、NAS 位置、腾出空间），由对账生成，归档后最迟下一分钟出现。问题进 `⚠️ 同步出错.txt` 的归档栏。

**调度**：守护进程启动 2 分钟后跑一轮，之后每 24 小时一轮；单飞；出错只记日志不退出。和 60 秒一次的「我的内容」对账共用进程内互斥（`storage-mutex.ts` 的 `runExclusive`），两者排队，不同时碰同一个项目。

不做：归档后自动从 NAS 取回、编辑工程在 NAS 上的可恢复性验证（剪映工程里的本机绝对路径不改写）、多工作区、设置界面。
