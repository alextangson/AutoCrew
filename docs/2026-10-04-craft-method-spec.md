# 传播方法：拆解库 + 用户原话 — 规格

2026-10-04。创始人已确认。

## 目的

写稿流程里没有任何关于「什么会爆」的理解：只有禁忌规则，没有正向方法。这次补三样，都以真实数据为依据，不编套路：

1. 一页「中长视频留人方法」：从对标博主的拆解里提炼出来。
2. 一页「底层传播原理」：每条原理都用拆解里的真实片段举例。
3. 每篇稿都有的「用户原话」：立意和开头从这些原话里来。

## 创始人决定

- 参照博主：YouTube 的 Dan Koe（@DanKoeTalks）。只借结构和留人手法，不借选题和口吻。
- 长度换算：他的视频 25–50 分钟，我们是 7–10 分钟。他每隔几分钟重新钩一次观众，我们压到每 1–2 分钟一次。
- 用户原话：抖音用创始人已登录的 ego 浏览器只读浏览；YouTube 用 yt-dlp 抓评论。
- 存放：
  - 抓取工具进仓库，和其他工具一样能自检。
  - 博主的字幕原文只放本机缓存 `~/.cache/autocrew-yt/craft/<博主>/`。
  - 拆解卡和方法页放资料库 `<资料库>/workspaces/default/craft/`。卡里只写转述，引用原话每处不超过 15 个字。
- 更新：按需。创始人说「再拆几条 / 加一个博主」时才跑，不定时。

## 一、抓取工具（进仓库）

`scripts/craft-fetch.mts`，在 package.json 里注册为 `npm run craft:fetch -- <频道或视频网址> [--top N] [--recent M]`。

- 用 yt-dlp 取视频列表。播放量需要逐条取元数据：列表页不带播放量。
- 每条视频取：标题、播放、点赞、评论数、时长、发布日期、热度条（`heatmap`）、人工字幕（没有就取自动字幕）、前 200 条热门评论。
- **串行抓取**，每条之间等 5–10 秒。遇到 429 就退避重试最多 3 次，仍然失败就标记这一条失败、继续抓下一条。失败原因要写进汇总，不能悄悄跳过。
- 每条视频输出 `<视频id>.json`（元数据、热度条、评论）和 `<视频id>.vtt`，再写一份 `index.json` 汇总成功和失败的条目。
- 热度条和字幕对齐：每个热度高峰、低谷前后各 20 秒对应的字幕片段，单独输出一份 `<视频id>.peaks.json`。
- `autocrew doctor` 加一项检查：yt-dlp 可用且版本不太旧，否则给出升级提示。

## 二、拆解库（内容，由 agent 完成；资料库）

用上面的工具抓 Dan Koe 8 条视频：近一年播放最高的 6 条，加最近 2 条。每条写一张拆解卡 `craft/dankoe/<视频id>.md`：

- 数据：播放、点赞率、时长；热度条的高峰和低谷，各附时间点和当时在讲什么（转述）。
- 前 60 秒：替观众说出了什么，立了什么判断，许诺了什么。
- 结构时间线：每段讲什么，用了什么手法重新钩住观众。
- 结尾怎么兑现开头的许诺。
- 我们能借的一招：要具体到可以照做。

在 8 张卡的基础上写 `craft/method.md`，控制在 1500 字以内，分两部分：

- **中长视频留人方法**：每条手法都标出出自哪张卡、哪个时间点。
- **底层传播原理**：人为什么点开、看完、转发。只写在拆解里找到实例的原理，每条附一个实例。

## 三、写稿流程接入

改 `skills/write-script/SKILL.md`：

- **第 2 步 调研**：先收 10–20 条目标用户的真实原话，来源是相关抖音和 YouTube 视频的评论、提问、吐槽，每条附出处链接。要在稿里用到的原话，用 `verify_quote` 登记。收不到就如实说明，不要编。
- **第 3 步 立意**：动笔前读 `craft/method.md`。每个立意的「开头 15 秒」必须从用户原话里来；「为什么可能爆」要说明用了方法页里的哪一招。
- **第 4 步 写**：按方法页安排开头许诺、中途重新钩人、结尾兑现。

`autocrew_draft start` 的返回里增加 `craft_method`：资料库里有 `method.md` 就附上正文，没有就返回 null 并提示「还没有拆解库」。

Codex 审稿提示词（`codex-review-prompt.md`）：把方法页作为「开头」和「收获」两项的判断参考。判据仍然只有三项，不新增。

## 边界

| 情况 | 处理 |
|---|---|
| 没装 yt-dlp | `craft:fetch` 报错并给出安装提示；`doctor` 显示这一项不通过 |
| 被限流（429） | 退避重试最多 3 次，仍失败就标记失败、继续下一条，汇总里列出 |
| 视频没有字幕 | 拆解卡标注「无字幕，只拆数据和结构」 |
| 视频没有热度条（新视频或小视频） | 卡里标注「无热度条」，不编数据 |
| 资料库里没有方法页 | `start` 返回 null；技能照常写，但要告诉创始人还没有拆解库 |
| 抖音评论抓不到（没登录、页面变了） | 如实告诉创始人，改用 YouTube 评论或搜索结果，不编 |

## Codex 会审吸收（14 条；与上文冲突时以本节为准）

1. **热度条 ≠ 留存。** 一律叫「重看强度」，只描述「观众在这里反复回看」，不推断留住了谁、流失了谁。`peaks.json` 照做（便于对字幕），但拆解卡里不写因果结论。
2. **只是假设。** 8 条成功视频只能提炼「结构假设」，不叫「传播规律」。`method.md` 每条手法标「假设」，并写明怎么用我们自己的账号数据（`context.hits`）去验证。
3. **用户原话改成限时、建议性。** 调研里收用户原话控制在约 10 分钟，能收几条算几条，不要求凑满数量。开头可以从用户原话出发，也可以从创始人素材或我们的判断出发，但不能是 AI 想象的场景。方法页是参考，不是硬规矩。
4. **评论不走 verify_quote。** 抖音评论（ego 浏览器）和 YouTube 评论（yt-dlp）只作调研线索，写进稿件时一律当未核验材料处理，不登记成已核验证据，也不改核引文的逻辑。
5. **前提要说准。** 现有流程已经会查爆款和账号数据；缺的是「可复用的结构范例」，规格的目的写成这个。
6. **先给明确视频，不爬频道。** 第一批由 agent 先从频道列表挑候选（最多看 30 条，排除 Shorts 和直播，按近一年和播放筛），把 8 个网址列给创始人过目，再用工具抓这 8 条。工具只接受明确的视频网址列表，不做全频道排名。
7. **抓取范围写死。**
   - 字幕：先取人工英文字幕，没有再取自动英文字幕，不取翻译轨；滚动字幕要去重。
   - 评论：默认不抓。只在加 `--comments N` 时抓热门评论，不抓楼中楼，N 最多 100；评论关闭就标注。
   - 缺失的数字照实写缺失。
8. **限流处理。**
   - 整次运行共用一个重试预算：最多 3 次，退避重试。
   - 连续 2 次 429 就整体停下，把已完成的部分照样写盘，可以断点续抓。
   - 每个子进程设超时。
   - 字幕成功、评论失败时保留字幕。
9. **没字幕就只出数据卡。** 不靠猜测拆结构，卡上标「无字幕，结构未拆」。
10. **接入方式。**
    - `start` 通过 `getDataDir(a.dataDir)` 读 `craft/method.md`，最多 6000 字。
    - 区分两种情况：文件不存在返回 null；读失败返回错误原因。
    - 拆解卡和原始抓取一律不进写稿上下文。
    - Codex 审稿提示词加一个可选占位 `{{CRAFT}}`，技能负责把它替换掉。
11. **doctor 里 yt-dlp 是可选项。** 只跑带超时的 `--version` 并显示版本，不影响 doctor 的退出码，也不联网查更新。
12. **工具实现。**
    - 用 Node 的 `execFile` 调 yt-dlp，不经 shell。
    - 只接受 YouTube 视频网址。
    - 禁止下载媒体（`--skip-download`），并加 `--ignore-config`。
    - 抓取结果和测试替身不进 npm 包。
13. **合规。**
    - 只在本机缓存中保留字幕全文，缓存可以用 `npm run craft:fetch -- --clean <博主>` 删除。
    - 评论只保留正文和点赞数，不保留用户名和头像。
    - 引用原话越少越好。
    - 不绕过任何访问限制。
    - 平台条款创始人另行确认。
14. **测试放在 `src/` 下**，核心逻辑写成 `src/modules/craft/*`，脚本只是入口，这样 vitest 能跑到。
    - 要覆盖：方法页加载、审稿占位替换、部分结果写盘、字幕去重、超时。
    - 验收接受「这批没抓全」的诚实结果。

## 不做

- 不做定时抓取，不做看板。
- 不把博主的字幕原文放进仓库或资料库。
- 不新增审稿维度。

## 验收

1. `npm run check` 全绿；`craft:fetch` 有测试：用替身代替 yt-dlp，覆盖成功、429 重试、无字幕、无热度条、汇总里有失败条目。
2. 真跑：抓 Dan Koe 8 条视频，汇总里列出成功和失败的条目；8 张拆解卡和 `method.md` 写进资料库，交创始人过目。
3. 写稿接入：`start` 返回 `craft_method`；技能第 2、3 步有用户原话和方法页的要求。
