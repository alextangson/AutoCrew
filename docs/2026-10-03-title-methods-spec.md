# 发布标题方法库 — 规格草案（待创始人确认）

2026-10-03。来源：dbskill 的小红书标题公式 + 创始人早年做 IP 时的标题方法论（装修领域），两边只取方法，用我们自己的话重写，例子换成自家场景。

## 已定

- 方法库四平台通用（小红书 / 抖音 / 视频号 / B 站），只有字数和语气按平台调。
- 每次出发布包，标题给 3 个候选，分属不同方法，创始人挑。
- 试用期 4–8 条，之后按数据留、改、删方法。
- 旧的字符串拼接标题生成器（`src/modules/writing/title-hashtag.ts` 里的 `generateTitleVariants` 等）换成新方法库。
- 不标出处。

## 一、核心思维（写标题前先过这三步）

1. **对一个人说话，不是对一类人。** 推荐是一条一条推到某个具体的人面前的。标题要让刷到的那个人觉得「这是在说我」。
2. **写前三问**：谁在看？TA 此刻在想什么？TA 想要什么？
3. **用画像，不用人群词。** 不说「职场人」，说「天天被老板催周报、听说 AI 能写但试了两次都不像样的运营小林」。画像直接用 AutoCrew 已有的受众档案（小林 / 老陈 / 老周），不另造。

## 二、方法（8 类，约 16 个方法）

每个方法在库里写清：公式、为什么有效、适合什么稿、不适合什么稿、一个自家场景的例子。下面只列骨架。

| 类 | 方法 | 公式骨架 | 底层心理 |
|---|---|---|---|
| 共鸣 | 真诚对话 | 坦白一件事 + 真实情绪 | 像朋友说话，降低防备 |
| 共鸣 | 精准镜头 | 具体人 / 具体场景 + 具体解法 | 「说的就是我」 |
| 结果 | 前后对比 | 原来的困境 → 改变后的结果 | 看到改变的可能 |
| 结果 | 结果承诺 | 数字 / 步骤 + 明确效果 | 降低行动成本 |
| 痛点 | 踩坑清单 | 警示词 + 常见错误 + 数字 | 损失厌恶 |
| 痛点 | 后果提醒 | 常见做法 + 你没想到的后果 | 紧迫感 |
| 好奇 | 认知冲突 | 大家都觉得对的事，其实不对 | 打破已有认知 |
| 好奇 | 反转惊奇 | 反常做法 + 意外结果 | 「怎么可能」 |
| 好奇 | 内行视角 | 只有做过的人才知道的 N 件事 | 信息差 |
| 好奇 | 抢先一步 | 多数人还没注意到的变化 + 现在该做什么 | 领先感 |
| 思考 | 一针见血的问题 | 观众真纠结的问题 + 暗示有答案 | 问题本身就是钩子 |
| 思考 | 二选一对比 | A vs B + 怎么选 | 帮做决定 |
| 思考 | 点破需求 | 你是不是也…… + 原因 / 解法方向 | 被说中 |
| 格局 | 小处见大 | 一个具体细节 + 连到工作 / 生活方式 | 提升格局感 |
| 身份 | 身份代入 | 点名一类人 + TA 专属的问题 | 自我归类 |
| 清单 | 一篇讲全 | 全面词 + 核心问题 + 数量 | 收藏动机 |

## 三、检验清单（每个候选都过一遍）

1. **针对性**：指向一个具体的人或场景吗？
2. **情绪**：能触发担心、期待或好奇吗？
3. **价值**：观众能拿走什么（省事、少踩坑、看懂一件事）？
4. **留悬念**：看完标题还需要点进来吗？答案全说完了就失败。
5. **张力**：对比、数字、悬念、冲突、结果承诺里至少占两样。
6. **真实**：见第四节。

## 四、真实性红线（我的提议，需要你确认）

你那份 IP 方法论里有几类写法，放进 AutoCrew 会和「只用有依据的事实」冲突，也容易被平台判标题党：

- **假稀缺 / 假时限**：「改天就删」「最后一波」「错过等一年」，内容其实不会删、不会限时。
- **编造的权威和比例**：「99% 的人都不知道」「顶级设计师都在用」「50w 人借鉴」，没有出处。
- **稿子里没有的数字**：「看完省 3 万」「让家看起来贵 10 万」，正文里没有这个数。
- **夸大的反应**：「同事都惊呆了」「设计师都要来偷师」，不是真事。

提议：这些**方法**保留（稀缺、权威、数字确实有效），但标题里出现的数字、权威、时限、他人反应，必须能在定稿或证据台账里找到。找不到就换方法，不硬套。

## 五、落点（改哪里）

1. **方法库数据**：一个新模块，存上面的核心思维、方法、检验清单和平台差异（字数上限沿用现有 `post_title` 上限；小红书可带 emoji，B 站可用【】，视频号和抖音少用 emoji）。
2. **出发布包**：`autocrew_pre_publish video_kit` 的说明里带上方法库。宿主模型先写 3 个通用候选（各标方法 id 和一句选它的理由），创始人挑一个，再按各平台字数和语气落成 `post_title`。kit 里记下这条用的方法 id。
3. **代码硬检查**（只拦能机器判断的）：
   - 超平台字数上限（已有，保留）；
   - 方法 id 不在库里；
   - 标题里的阿拉伯数字在正文里找不到（提示，不拦）。
4. **旧生成器**：删掉字符串拼接模板。平台改写工具（`src/tools/rewrite.ts`）改成返回方法库指引，由宿主模型写，不再用代码拼标题；平台规则（字数、话题标签）保留。
5. **试用期统计**：按方法 id 汇总已发布标题和点击率。数据从三平台数据回流取，回流没开就让创始人手填。

## 六、边界情况（这些也算交付范围）

- 3 个候选都不满意：可以要求再出 3 个，或者创始人自己写；自己写的标记为「自拟」，不算进任何方法。
- 创始人在候选基础上改了几个字：仍记原方法 id。
- 同一个视频四个平台标题不同：方法 id 按平台分别记。
- 稿件太短、太空，写不出有张力的标题：直接说内容撑不起，不硬凑。
- 方法 id 拼错 / 不存在：拒收并列出可用 id（按模型参数不可信的约定，先规范化再判断）。
- 试用期内同一方法连用：不拦，但每次候选必须分属 3 个不同类。
- 回流数据缺失：试用期报告如实写「无数据」，不拿空值算平均。
- 已发布的旧稿没有方法 id：统计时归为「未标记」，不回填猜测。
