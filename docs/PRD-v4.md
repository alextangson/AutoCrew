# AutoCrew PRD v4 — 自媒体创作者的新媒体数字员工团队（草案）

> 状态：**已裁决生效**（2026-07-07 创始人裁决 A–F，记录见 §10；D 修订原建议、E 附条件）
> 日期：2026-07-07
> 与 v3 的关系：**delta 文档，不整体取代**。凡未被 §2 处置表列为「修订/推翻」的 v3 裁决全部继承——护城河（v3 §3）、双层架构（v3 §5）、闭环机制与合规红线（v3 §6）、变现与定价（v3 §9）、引擎选型（v3 §14.4）。
> 一句话定位：**自媒体创作者的新媒体数字员工团队——一个总监带七名职能员工，跑在创作者自己的机器上，把「情报→成稿→素材→封面→审核→发布→回流→复盘」整条链做成默认值，越用越像你。**

## 0. TL;DR

- v3 的单流程纪律没有错，但它守住的那条流程（短视频口播）**最后一公里永远闭不上**（无发布 API，最后一步永远是人贴）；而真正已经端到端闭合、文案质量已被创始人本人认可的链（公众号，在 qingmoagent/openclaw 里）被 v3 §2 亲手排除。dogfood 停摆的根因不是缺员工，是**质量最好的链和产品不在同一个身体里**。
- v4 做三件事：
  1. 定位从「口播数字编剧」升级为「新媒体数字员工团队」；
  2. 团队模型 = 总监（外层调度的拟人化）+ 七名员工（状态机阶段的拟人化），**逐个转正制**——架构仍是 v3 双层架构，禁止 agent 互聊；
  3. UI 从「创作者指挥台」升级为经营面板（对标 Polsia 消化后的裁决，见 §7）——dashboard 是经营循环的读模型，核心组件是**待审队列**，不是 activity feed。
- 从哪里改起（P0）：把 qingmoagent 已验证的文案流程与公众号发布链移植进 AutoCrew 本体。dogfood 期唯一北极星 = **采纳率**。质量过了「值得改」阈值，纠正飞轮才有输入；总监的定时循环（"睡醒有稿可审"）必须排在文案转正**之后**——否则是每天早上三篇不想看的稿，负体验加速器。

---

## 1. 为什么改：dogfood 停摆的根因链（证据，不是感觉）

1. 创始人 dogfood 无动力，原话：「写出来的文案不符合预期，我就不想改动了」。
2. 纠正是飞轮的唯一燃料（v3 §3 护城河的输入端是编辑信号）。稿件质量低于「值得改」阈值时，纠正数 = 0，飞轮空转，闭环数据无从谈起。dogfood-runbook 实战日志停在 6 月中旬，与此吻合。
3. 与此同时，qingmoagent（openclaw 线上版）的文案质量被创始人认可；公众号发布全路径已验证（`wechat_publish.py`：图文、配图生成、封面兜底、推草稿箱）——openclaw-integration-blueprint（2026-03-31）早已把它列为 P0 复用资产。但 v3 §2（2026-06-10）把公众号明确排除出 v1（「交给 musegzh」）。
4. AutoCrew 自己的 publish.ts 里唯一非 stub 的路径恰恰也是公众号草稿（v3 §1 核对死因时白纸黑字写过）。
5. 结论：**问题不是链条缺环节，是把已验证的质量和唯一能全闭合的发布路径关在了产品外面。v4 第一优先级是合体，不是扩编——扩编是合体之后的事。**

## 3. 定位（升级）

- 一句话：**自媒体创作者的新媒体数字员工团队。**
- 与 v3 的差：v3 卖一个员工（数字编剧），v4 卖一个部门。但「部门」在 dogfood 期是**逐个入职**的——每个员工用上一个员工产生的质量数据换编制。
- 北极星不变（这就是 AutoCrew = auto + crew 名字的兑现），变的是路径：不再等「单流程飞轮证明复利」这个无判据的模糊条件，改为每个员工有量化转正门槛（§4 编制表）。

## 4. 团队模型

### 4.1 组织架构（呈现层）↔ 执行架构（状态机）的映射

- **总监** = v3 §5 外层编排（调度器 + 计划循环 + 人类确认门）的拟人化。
- **员工** = 流水线阶段 + 各自技能包（skills/tools）的拟人化。

**红线（继承 v3 双层架构裁决，逐条写死）：**

1. **禁止 agent 互聊。** 员工之间不存在对话，只存在状态机上的产物交接（情报员产出选题卡 → 文案读选题卡）。总监的「调度」= 确定性规则 + 单次规划 prompt，不是常驻多 agent 会话。v1 死于基础设施野心，多 agent 自由会话就是那个野心的 2026 版。
2. 每个员工动作 = 一次显式状态迁移，落盘可恢复；跨人工/跨时间边界必须是 `awaiting_*` 状态（v3 原文不变）。
3. **逐个转正制**：员工先以最小形态入职（通常 = 一个技能 + 一种卡片），转正门槛量化（见编制表）。**未转正的员工不进 presence 条——UI 不许展示不存在的劳动。**

### 4.3 文案组架构裁决：一引擎 × N 平台包 × 严格单平台上下文隔离

> 背景：创始人实测「1 个 agent 写多平台容易串，质量不佳」。诊断：串稿的根因是**上下文污染**——同一会话里连写多平台，前一个平台的语气残留在上下文里。N 个独立 agent 能止血只是因为顺带做了隔离，但代价致命：把最值钱的学习数据（创作者的声音与纠正）切成 N 份，dogfood 数据量下每份都喂不饱，风格飞轮永不收敛。

裁决：**既不是 1 个 agent 切 playbook，也不是 N 个独立 agent。**

1. **两层拆分，正交存储**：
   - **声音内核**（一份，跨平台共享）：用词癖好、口头禅、立场、禁忌、招牌表达——per-creator 护城河本体（v3 §3），绝不按平台切分；
   - **平台包**（每平台一个）：结构骨架、长度、格式规范、钩子集、hashtag 惯例、该平台的成功指标——v3 §8 赛道包抽象的平台维度延伸。
2. **生成时严格隔离**：每次生成 = 全新短时 loop（v3 §5 内层原语），上下文只注入「声音内核 + 当前一个平台包 + 选题/brief」。**禁止同一上下文连写两个平台**——一稿多发 = N 次独立生成，不是一次生成 N 变体。串稿在架构上被杜绝，与 agent 数量无关。
3. **纠正路由**：纠正默认记入发生纠正的平台包；同一模式在 ≥2 个平台被纠正 → 自动升格进声音内核。（这个二分类是 §7.2a LLM 风格建模的新增职责。）
4. **呈现层 = N 个写手 persona**：每个平台包携带一个 persona，卡片署名到席位，各席独立转正（该平台采纳率）——未转正席位不进 presence 条，与 §4.1 红线 3 一致。
5. **新平台的边际成本 = 写一个包**：种子 playbook 来自情报员的对标拆解卡（拆解 → 包，内部闭环——拉片/拆解不只喂选题，还喂平台包的初版与迭代）。平台包按转正制排队入列，不一次铺六个。
6. **出海平台（Twitter/Reddit）单独警示**：不只是新包，是**第二个声音内核**——中文声音不直接迁移到英文，跨语言声音建模是开放问题（裁决点 F）。

### 4.4 入职次序（这就是路线图）

文案组·公众号席（P0，合体）→ 发布员-公众号（P0，链闭合）→ 总监 L2 循环 + 指挥台事件流改造（P1）→ 文案组·口播席 + 情报员扩编（对标拆解/监控）+ 封面设计师（P1.5）→ 素材索引/生成（P2）→ 发布员扩平台（B 级预填，过 §6 风控评审后）+ 文案组扩席（P2）→ 剪辑师（裁决点 C）。

## 5. 平台策略（修订 v3 §2）——裁决点 A

**公众号回归，升为 P0 验证链。** 理由：

1. **唯一有官方草稿箱 API 的平台。**「官方 API 没戏」对抖音/小红书/视频号成立，对公众号不成立——且两个代码库里各有一条已验证实现（publish.ts 草稿路径 + `wechat_publish.py` 全路径）。
2. 发布环节能真正闭合的链，才能验证「数字员工团队」的完整体感；短视频链的最后一步在可见未来永远是人贴。
3. 文案质量已在该平台被 0 号用户（创始人）验证。

**短视频口播不降级**：数据回流 runbook 照跑，赛道包抽象（v3 §8）本来就为多形态设计。变化只是分工：**全链自动化的验证在公众号上做，数据飞轮的验证继续在短视频上做**——两链共享文案/风格/合规/分析师员工。公众号图文顺手成为第二个声明式赛道包，正好证明 pack 抽象（v3 §8 要求的那一步）。

**musegzh 处置（裁决 E，2026-07-07）**：暂不归档，继续稳定运行。归档触发条件 = AutoCrew 公众号链在**过程可视化**上超过 musegzh——musegzh 的真实短板不是质量，是黑盒（创始人原话：工作是黑盒，看起来很不方便）。因此「白盒可视」升格为 P0 验收项（§8）。**AutoCrew 替代 musegzh 的资格线不是写得更好，是让创始人看得见、改得动。**

## 6. 发布员 × v3 §6 红线：能力分级表

> v3 红线 1 原文：「任何写操作（含发布表单预填）需独立风控评审 + 默认关闭的 opt-in + 用户对每次提交显式确认」。本表即该评审的输入格式；B 级开启前逐平台单独过评审。

| 级别 | 平台 | 机制 | 人的角色 | 红线符合性 |
|---|---|---|---|---|
| **A 全自动到草稿** | 公众号 | 官方草稿箱 API | 在平台后台点「发表」 | 不触 §6（官方接口，非浏览器自动化） |
| **B 表单预填** | 抖音 / 小红书 / 视频号 | 扩展 content script 预填标题/正文/tag/封面 | **逐次显式确认 + 亲手点发布** | 红线 1 预留的演进空间；默认关闭，每平台单独 opt-in |
| **C 纯手动** | 新平台 / 评审未过 | per-field 复制（现状） | 全手动 | 现状 |
| **D 全自动发布** | — | — | — | v4 不做（L3 远期定位不变） |

「agent 模拟人类去发」在 v4 语境下 = **B 级，不是 D 级**。发布员的"能干"以人最后一击为边界。

**评审时机（裁决 D，2026-07-07）**：B 级风控评审在 v4 内即启动，与 P0 并行（逐平台出评审文档：暴露面、ToS、风控信号、回滚策略）；B 级**实施**仍排 P2，评审通过是实施前提。

## 7. 指挥台 UI 规格 v2（取代 v3 §7.3 及 S2.8 / S3.0 增补）

### 7.1 继承的红线（不变）

裸 chat 框禁止（差异化住在结构化卡片和闭环数据里）；onboarding 永不阻断；绝不在 onboarding 问 API key；功能屏堆叠（工具感不是员工感）仍是反模式。

### 7.2 修订：模态弹窗红线细化

原红线「模态弹窗打断对话流」拆成两半：

- **对话流内的确认门必须是内嵌卡片**（不变）。
- **对象管理面板允许模态**（账号 / 素材详情 / 域名 / 设置类）——Polsia 的 Manage Domains 即此类。

判据一句话：**弹窗关闭后世界不变 = 允许；弹窗里承载不可逆决定 = 禁止**，改用卡片确认门。

### 7.3 新增裁决（对标 Polsia 的消化结果，不是像素级抄）

1. **Dashboard = 经营循环的读模型。** 一切「活着」的元素（presence、流式工作日志、"xH AGO"、计数器）只能由引擎真实事件驱动。**前置架构依赖：引擎→UI 事件推送通道（IPC push，替代拉取式 `today:summary` 单打）+ 渲染层单一 store + 订阅渲染**——在铺第二批组件之前完成。renderToday 重入守卫、chatBusy 手工锁这类补丁不许再繁殖：竞态数量随组件数平方增长，这是架构债不是 bug。
2. **核心组件是待审队列，不是 activity feed。** 我们的交互语法 =「AI 备好 → 人过审 →（分级）发布 → 催回填」，与 Polsia 的「AI 干了 → 人围观」根本不同，因为我们的平台没有它那样的 API（§6）。待审队列 + 回填提醒 + 回填拖延告警是 Polsia 没有而我们必须有的三个组件。
3. **IA 主轴 = 内容条目（11 态 pipeline）× 平台变体。** 员工是视角不是主轴：点员工头像 = 过滤到该员工经手的条目。多账号维度 schema 预留 `account_id`，UI 后置。
4. **视觉立场一次定死，落成 design token 层再动组件。** 方向：编辑部风——衬线展示标题 + 等宽标签/按钮 + 近黑白 + 发丝线分隔 + 顶部工作日志。禁止引入通用组件库（shadcn 类做不出这个味道，且违背克制原则）；Electron 现壳完全够用，**禁止以「丑」为由重写壳子**。
5. **Chat 的位置**：今日命令栏（入口）+ 任务会话视图（深度交互）。Polsia 把 chat 缩到右下角一个小框，恰好从外部验证了 v3 反裸-chat 裁决——价值住在组件里，对话只是入口。
6. **组件 ↔ 员工映射**（指挥台一屏）：顶部流式日志 + presence 条 = 总监；雷达卡 + 拆解卡 = 情报员；待审稿队列 = 文案 + 审核员；封面候选卡 = 封面设计师；发布队列 / 回执 = 发布员；回流报告 + 归因卡 = 数据分析师。**未转正员工不出现在面板上**（§4 红线 3）。

### 7.4 反模式清单 v2（评审用）

裸 chat 框；功能屏堆叠；onboarding 阻断墙；首跑暴露 API key；对话流内模态确认门；**假活性**（没有引擎事件却做出「在干活」的动效）；**展示未转正员工**；以视觉改版为名重写应用壳。

## 11. 交付形态裁决（2026-07-08，创始人）——本地 server + 浏览器 dashboard，取代 Electron 窗口

> 取代 v3 §14.1「Electron 窗口」的交付形态部分（引擎选型 §14.4 自研薄 loop 不变）。动机：dogfood 阶段创始人要 Polsia 式浏览器 dashboard；Electron 每次改前端要重建重启、单窗、包重，且"变化不大"的体感半来自此。

**裁决：AutoCrew 前端从 Electron 窗口搬进浏览器 tab,引擎抽成本地 HTTP + SSE server。**

**红线(命根子,不可越):server 跑在用户本机,不是云。** Polsia 后端在云上因其全是 API 生意;AutoCrew 护城河是浏览器自动化读用户自己的平台后台 + 公众号发布碰本机脚本/登录态(§6),只能本地执行。形态 = 长得像 Polsia 的浏览器 dashboard,但进程在用户机器上。**"搬去云"= 护城河消失,永久禁止。**

**为什么这是往护城河走,不是背离:**
- 工作日志事件流从 Electron IPC push 变 SSE——更干净,且 SSE 就是"AI 在干嘛实时可见、不黑盒"的标准做法(§7.3-1 白盒资格线的天然载体);
- 回填数据的浏览器扩展(§6)本来就活在浏览器,dashboard 同处浏览器更顺;
- §9「网页工具当流量入口」漏斗与浏览器前端天然贴合。

**代价(已知,不装看不见):**
1. 非技术创作者打包以后稍麻烦(开 server + 开 localhost vs 双击);可解(菜单栏启动器 / 以后套只加载 localhost 的薄壳),非 dogfood 阶段问题;
2. 素材库「引用本地大文件不复制」(2GB 视频)——浏览器不给 JS 本地路径,需单独绕(拖拽 / 本地助手);
3. 安全:server 绑 `127.0.0.1` + 启动 token(防 DNS-rebinding / 同机他进程),必做。

**基本不浪费:** 44 IPC 通道 → HTTP/SSE 端点(机械改名,复用 `buildIpcHandlers()`);引擎模块(赛道包/Gate/发布/事件总线)一行不动(本就 electron-free 有测试);渲染层 HTML/CSS/JS 九成搬;`event-hub` 注入式 broadcast → SSE。**唯一真扔:`desktop/main.ts` → 一个 Node 原生 http server(不新增依赖)。** Electron 降级为「以后可选的壳」,不是地基。

**同期 IA 落定(§7.3 UI 规格 v3 增补):三栏 = 内容流 | 大工作台 | 总编辑对话。** 五页导航(今日/选题/内容/数据/素材)作废——按「想法→写→改→发」流程组织,总编辑对话常驻右侧贯穿全程;定位挪进设置(低频设一次);数据/素材上下文出现,不占日常导航。
