# 体裁手册 + 版本管理｜实现方案（草案，待创始人确认）

背景与依据：`docs/reports/2026-10-13-抖音精选对比与写稿方法论.md`。手册初稿：`docs/playbooks-draft/*.md`（5 本）。

## 已定（创始人 2026-10-13）

- 五种体裁各一本手册：干货方法、实验演示、反常识判断、信息差/产品、人物故事。
- 立意卡每张标一个体裁，选卡即选体裁；一条稿只认一本主手册。
- 实验演示缺亲历：停下问创始人；他说先不做，就改走信息差或干货方法。
- 手册改动进「等你拍板」，看改前改后再批；批了生成新版本。
- 单本手册回滚、随时可回滚（页面标样本够不够）；回滚 = 把旧版内容存成新版本，历史不删。
- 改稿轮数只算创始人提意见的轮次；10-04 前的老稿不归版本。

## 1. 存储

```
<dataDir>/playbooks/
  manifest.json             # 每本：id、名称、当前版本号、版本列表、待批提案、决定日志
  <id>/v<N>.md              # 每个版本一份全文，只增不改
```

- `id` 固定 5 个：`ganhuo` `shiyan` `fanchangshi` `xinxicha` `renwu`。v1 不支持新增或删除体裁。
- 版本条目：`{version, at, author:"founder"|"agent", kind:"seed"|"edit"|"rollback", founder_words, reason, based_on, rolled_back_to?}`。
- 写入顺序：先写 `v<N>.md`，最后写 manifest。全部经 `json-atomic` 的原子写 helper（自带资料库写锁检查）；同一数据目录内按队列串行。
- 读取要区分「文件不存在」和「读坏了」：manifest 解析失败要报出可见错误，不当成空、不覆盖（creator-profile 现在有静默清空的坑，这里不复制）。
- 种子：仓库新增 `templates/playbooks/*.md`（产品自带默认 5 本）。首次读取时如果资料库里没有 `playbooks/`，就把这 5 本种进去作为 v1（author: agent，kind: seed）。创始人这套从 `docs/playbooks-draft/` 定稿后，作为仓库默认版本。
- 每本上限 4,000 字，超过的提案直接拒绝。

## 2. 接进写稿流程（`autocrew_draft` + `write-script` 技能）

- **`start`**：`context` 新增 `playbooks_index`，即 5 本的名称、「什么时候选它」一段、当前版本号，不带全文。`craft_method`（`method.md`）是否继续加载，待定，见第 6 节问题 1。
- **`angle`**：新增必填参数 `genre`（5 个 id 之一）。存盘时在 `draftPath.angle` 记下 `playbook: {id, version}`，回执里返回这本手册的全文。重新出立意、换了体裁时，重新记录。
- **断点续写**：`progress` 带上已记录的 `playbook {id, version}` 和全文，写稿一直用立意时那个版本，中途手册升级也不换。
- **旧稿兼容**：立意里没有 `genre` 的老稿照常续写，记为「未归版本」，不参与统计。新出的立意必须带 `genre`。
- **Codex 审稿**：`codex-review-prompt.md` 里的 `{{CRAFT}}` 换成选定手册的全文。
- **技能文本**（`skills/write-script/SKILL.md`）：
  - 第 3 步立意卡加四样：体裁、一手素材、贯穿例子、爆点（以及它出现在第几秒）。
  - 实验演示缺亲历时，按上面已定的规则处理。
  - 第 5 步：创始人的意见如果是针对某种体裁的写法，`lessons` 的 `scope` 用 `playbook:<id>`。
- **工具说明预算**：`mcp/tool-surface.test.ts` 的总预算目前只剩约 80 字，加 `genre` 参数和新工具都要抬高预算。这是有意的改动，在提交说明里写清楚。

## 3. 手册改动：提案 → 等你拍板 → 新版本

两种提案：

1. **意见补充（自动）**：写稿时 `lessons` 的 `scope` 是 `playbook:<id>`，就不进创作者档案，而是在那本手册上挂一条待批提案，内容是这条意见原文加创始人原话。批准后，把它追加到手册末尾「## 创始人补充」一节，生成新版本。整个过程不调模型、结果确定。
2. **整本修订（agent 发起）**：创始人说「把干货方法手册整理一下」或「按这几条改手册」时，agent 交一份整本新文本加修改理由，作为一条提案。

两种提案的共同规则：

- 提案绑定 `based_on` 版本，`gen` = hash（提案 id、based_on、提案全文）。批准时，如果手册已经不是 `based_on` 那一版，就返回 `stale`，必须重新提案，不能叠到更新的版本上。
- 「等你拍板」新增类型 `playbook_change`：可在对话里决定，动作为 `approve_playbook` / `reject_playbook`。brief 里给出改前改后的对比（只列有改动的段落）和创始人原话。
- 幂等照 `writing_rule` 的做法：在 `chatDecidable` 里加上这个库级类型，在 `commit()` 里短路到手册专用的提交逻辑，决定日志用 `eventId = "chat-<request_id>"` 存进 manifest，崩溃后可以重放。
- 拒绝的提案留在日志里，同一段文字不再重复提案（和规则的 tombstone 同理）。

新增一个小工具 `autocrew_playbook`，动作如下：

| 动作 | 用途 | 要求 |
|---|---|---|
| `list` | 列出 5 本手册：当前版本号、待批提案数 | — |
| `get` | 读某一版的全文 | — |
| `propose` | 提交整本修订 | 带 `based_on`、全文、理由 |
| `rollback` | 回滚到旧版本 | 必须带 `founder_words`、`to_version` |

回滚由创始人发起、可以撤回（撤回就是再回滚一次），所以不走「等你拍板」，直接生成新版本并记下原话。回滚时，挂在当前版本上的待批提案自动变成 `stale`。

## 4. 统计（每个版本的表现）

- **快信号：改稿轮数。** 一条稿的轮数 = `draftPath.feedback[]` 里带 `founder_words` 的条数。只统计已经 `prepare_final` 的稿；写到一半放弃的稿单独计数，不进中位数。每个版本显示：已定稿条数、轮数中位数、最少和最多。
- **慢信号：发布数据。** 按「稿件 → 发布作品」的绑定，找每个版本下已发布的抖音作品，取 D+3 和 D+7 正好那天的快照（没有就留空，不拿别的天代替），显示 2 秒跳出、每千播分享、每千播收藏，以及精选标记（有回流字段就显示）。
- 定稿少于 3 条或发布少于 3 条，就标「样本不够」，不显示好坏比较。只摆数，不自动下结论。

## 5. 后台页面

在设置的「更多」里新增「写作手册」页，和「品牌校准」并列：

- **列表**：5 本手册，每本显示当前版本号、更新时间、待批提案数。
- **单本详情**：
  - 当前全文；
  - 版本历史：谁改的、创始人原话、理由；
  - 对比：选中的某一版对当前版本（见第 9 节第 9 条）；
  - 每个版本的统计（第 4 节）；

- **待批提案**：在本页也能批，和规则在「品牌校准」页能批是同一个道理。走浏览器 session 专用接口，照 `rule-approval.ts` 的写法。

## 7. 刻意不做

- 不做在线编辑框，改手册只走对话和提案。
- 不自动判断「新版本变差了」、不自动回滚，只摆数。
- 不做体裁的新增或删除（v1 固定 5 本）。

## 8. 验收清单

- 首次读取会种进 5 本 v1；manifest 解析失败时，报出可见错误、不覆盖文件。
- 新立意不带 `genre` 被拒，回执列出 5 个合法 id；`genre` 写错同样被拒。
- 立意时记下的版本，在续写、Codex 审稿、`prepare_final` 全程不变，手册中途升级也不变。
- 同一个提案批两次只生效一次；用同一个 `request_id`、不同内容提交，返回 `request_conflict`。
- 提案的 `based_on` 版本已过期时，批准返回 `stale`，手册内容不变。
- 回滚生成新版本，历史完整保留；回滚到当前版本，直接报错；回滚后挂在当前版本上的待批提案变成 `stale`。
- 超过 4,000 字的提案被拒。
- 改稿轮数只数带 `founder_words` 的轮次；未定稿的稿不进中位数；样本少于 3 条标「样本不够」。
- 写入时资料库没连上或本进程不是写入方：报错，不写半截。
- 10-04 前的老稿和没有 `genre` 的旧立意显示「未归版本」，能正常续写。

## 9. Codex 会审意见及处理（2026-10-13，全部采纳；与前文冲突时以本节为准）

1. **（P1）技能和审稿提示词与手册冲突。**
   - `SKILL.md` 现在写着「写作规则只有档案」；`codex-review-prompt.md` 拒绝场景演绎开场，把 `{{CRAFT}}` 当可选参考。
   - 处理：明确两者的分工。档案规则是**通用底线**（说人话、真实、不编亲历、不撞车、口播格式），任何体裁都要遵守。手册管**结构**（开头、中段、收获、收尾）。两者在结构上冲突时，以手册为准。
   - 改写 `SKILL.md` 的硬规矩和第 3–6 步，删掉所有 `craft_method` 相关说明。
   - `codex-review-prompt.md` 改成「对照选定手册审主线、爆点、开头」，删掉跟手册冲突的固定判据。
2. **（P2）种子写到一半中断后无法恢复。**
   - manifest 是唯一的提交点。没有 manifest 就（重新）种：已存在、且字节和种子一致的文件保留；已存在但字节不同，就报可见错误，不覆盖。
   - 所有 `v<N>.md` 只写一次。目标已存在且内容不同，直接拒绝。
3. **（P2）`prepare_final` 不等于定稿。**
   - 「已定稿」= 创始人在工作台点了「定了」（`draft-finalize` 的有效定稿）。
   - 没定稿的稿显示为「进行中」条数，不算轮数中位数，也不判定为「放弃」。
4. **（P2）换体裁后，之前的改稿轮数被算到新手册上。**
   - 每条 `draftPath.feedback[]` 记录写入时，都带上当时的 `playbook {id, version}`；定稿时也记一份。
   - 一条稿归到它定稿时的那本、那一版手册；轮数只数跟这一版对得上的反馈。换体裁之前的轮数单独显示「换体裁前 N 轮」，不进统计。
   - 用同一体裁重新出立意时，保留原来记下的版本，不升级到新版。
5. **（P2）手册类意见缺完整的批准流程。**
   - `scope: playbook:<id>` 的 lesson，结果为 `playbook_proposed | playbook_duplicate | blocked_by_rejected`，回执带提案 id。
   - 和一条还在待批的提案文字完全相同，算 duplicate。手册类意见不支持 conflict 关系。
   - `prepare_final` 的 `pending_lessons` 也包括这篇产生的手册提案。
   - `review_inbox list{content_id}` 要能列出来源是这篇稿的库级条目（`playbook_change`，顺手把 `writing_rule` 也带上）。
6. **（P2）崩溃重放要放在查找之前。**
   - 和规则恢复一样，手册决定先按 manifest 的事件日志恢复，再调用 `locate()`。
   - 补一个测试：manifest 已提交、请求结果还没落盘时崩溃，重试要返回原来的成功结果，而不是 `already_handled`。
7. **（P2）回滚缺并发和重试保护。**
   - 回滚必须带 `expected_current_version` 和 `request_id`（作为 eventId）。两项都在 manifest 的串行队列里检查，浏览器和工具两个入口共用一套逻辑。
   - 当前版本对不上，返回 `stale`。同一个 request 重试，重放上次的结果，不会再生成一个版本。
8. **（P2）「旧稿不归版本」没有能执行的定义。**
   - 不按日期判断。只看有没有记下的版本：`angle.playbook` 不存在，就是未归版本。
   - 旧稿重新出立意后会记下版本，但它之前的反馈没有版本标记，按第 4 条自然不进统计。删掉前文「10-04 之前」的日期判定。
9. **（P3）砍掉「任意两版对比」。**
   - v1 只做两种对比：提案对它的 based_on 版本，选中的某一版对当前版本。两种共用一个对比渲染组件。
