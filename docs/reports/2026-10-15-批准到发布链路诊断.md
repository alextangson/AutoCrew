## A. 根因

类比：系统有一本「正式账本」（production.json：认稿 / 成片批准 / 封面批准 / 登记），会话里的确认被记在 Codex 自己的「便签」（项目里的 json 文件）上。发布检查允许拿便签顶账，打包只认账本，于是每次都只能走「例外」。

### 根因 1（流程缺一步 + 引导指错）：这条稿从没认稿，整个制作期都在「写稿段」，对话审批对它没有挂载点

**数据**
- `production.json.decisions` 13 条，只有 `candidate_confirm`、`ask_answer`、`storyboard_approval`。**没有 `script_approval`、`cut_approval`、`cover_approval`；`registrations` 为空。**
- `timeline.jsonl` 第 132 条：`stage_projected {from: drafting, to: published, rule: D1}`。稿件从 10-12 建稿到发布一直是 `drafting`，发布后才被对账投影成「已发布」，带徽章 `没走认稿`。
- 最后一次正文写入 10-13 09:29Z，之后没有交审。

**代码**
- `inbox.ts:413`：只有 `phase === "production"` 才出成片 / 封面审阅条目。
- `inbox.ts:385`：认稿条目只在 `draft_ready` 出现；`drafting` 连认稿条目都没有。
- `inbox.ts:405`：稿件一旦投影成「已发布」，认稿 / 成片 / 封面审阅全部不再出——本案发布后已无法从正常通道补批。

**修正（采纳 Codex）**：v1 说「死胡同、剪辑宿主没有权限」说过头了。`drafting → draft_ready` 是合法流转（`local-store.ts:1724`），模型禁区从 `approved` 开始（`production-hooks.ts:38`），交审只需要写稿认领令牌（`content-save.ts:437`）。所以准确说法是：**漏了「交审」这一步，系统提示（让剪辑方「先走审稿交上去」）指向了它不熟、也可能没有令牌的写稿流程**。Codex 当时是否拿得到写稿令牌，未核。

**用户影响**：对话里每一次「好 导出成片」「封面就……」「发布吧」都无处落账；发布时一律报登记缺失。

### 根因 2（调用遗漏）：剪辑宿主把批准写进了自己的文件，系统每次都提醒过

| 05:18:22 | Codex 把 v014 发给用户：「接得是否自然，还需你试听」 |

- 整个会话**从未调用 `autocrew_review_inbox`**；v005 之后的成片全部 `review:false`，`ready_marks` 只有 v005。
- `publish-plan.json.approved_covers[*].founder_quote` 用的是「OK 发布吧…」——发布授权被挪用成封面批准凭据。
- 请示的「通过」：分镜请示会同时写 `storyboard_approval`（`asks.ts:299-306`），但没有任何请示会写 `cut_approval`。Codex 拿到 6 次请示通过，容易误以为成片也批了。
- v014 的抽帧检查最后一次是 `unchecked`（原片对不上）。`approve_cut` 会在批准时**按当前输入重跑**检查（`decisions.ts:113-119`），所以修好原片对应就能过，不一定要「不查了」。

### 根因 3（接口设计缺陷，P1）：检查认例外，打包不认；例外还能换掉打包的封面

| 入口 | 判定 | 本案 | 认 overrides |
|---|---|---|---|
| `autocrew_publish check` | `deterministic.ts:83-87`：登记失败 → 两条**可例外** block | override 通过 | 认 |
| `ego_lite_prepare` 中间件 | `tool-runner.ts:72-117` 跑旧预检：`pre-publish.ts:410` 再判登记；标签 / 标题读平台发布包，没有发布包就读稿件字段（`pre-publish-kit.ts:32`）；全过后还有阶段门 | 登记 + 「无标签」两项 fail | 不认 |
| `ego_lite_prepare` 本体 | `ego-lite.ts:159`：`publishFiles()` → 登记出口 | 拒 | 不认 |
| `video_kit` | `pre-publish.ts:270`：`videoDone`（登记投影，`registration.ts:244`） | `video_not_done`，`next_action` 指向已关闭的 `autocrew_video register` | 不认 |

v1 之后 Codex 补出的三点（均已核实代码）：
- **登记错误码在检查里被丢掉**（`check.ts:59-62`）：`registrationState()` 只留错误文案，「从没批」「登记没提交」「登记的文件被换了」全被压成同一条可例外规则。
- **封面例外能换掉真正上传的封面**：登记有效时，`cover_registered` 例外可以放行一张不是登记那对的封面（`deterministic.ts:94-98`）；打包对成片核了登记路径，**封面却直接用计划里的**（`ego-lite.ts:171-187`）。这比「检查假通过」更严重：例外真能把未批的图发出去。
- **字节相同、路径不同的成片**：检查按字节比（`deterministic.ts:90`），打包要求绝对路径相同（`ego-lite.ts:174`）——检查过了，打包仍拒。

另外：`video_kit` 只是保存发布文案，本身不是发布许可；把它和发布判定绑在一起是额外的耦合。

### 根因 4（误导信息）：从未认稿也报「认稿已失效（正文改过或重开了）」

- `publish-gate.ts:54`：缺认稿、撤回认稿、正文改过、上一轮的认稿都归成同一句。
- Codex 据此向用户解释为「状态没同步」，并提出「登记例外」，而正确出口是「请你认稿」。
- 一个「登记例外」实际同时绕过认稿、成片批准、封面批准、登记四件事，问题文案只说了登记。

### 根因 5（降级，本案未触发）：成片 / 封面批准绑正文哈希

- `derive.ts:79-89` 确实绑 `body_hash`，创始人改稿只重绑认稿（`production-hooks.ts:76-81`）。
- **但 v1 说「改一个错字就让已批成片失效」过头了（采纳 Codex）**：认稿后进入制作段即冻结正文（`service.ts:85-93`），冻结后改正文被拒（`production-hooks.ts:65`），已有测试覆盖（`codex-seg1.test.ts:53`）。正常路径走不到。要改这条，得先找到一条真实的冻结绕过；目前没有证据。**撤回 v1 的 C-3。**
- 本案 `freezeIfNeeded` 不冻结，正是因为 `no_script_approval`（`service.ts:87`）——问题仍回到根因 1。

### 根因 6（回执语义混用）：`verified` 至少三种含义，计划文件被当成公开证据

**数据**：每平台 2–3 条 publish 事实。
- `record`（Codex 报的）：抖音 / 小红书 / B站事实上 `verified: false`、`claim_accepted: true`，但 `record` 返回给 agent 的是 `verified: true`（`record.ts:78-79`，含义是「这条说法被直接认」）。报定时、不带链接也会返回 `verified: true`（`receipts.ts:36-40`）。视频号短链没有作品形状规则（`post-publish-view.ts:24-34`），返回 `false`。
- `reconcile, obs_source: plan`：计划里 `publication.status: "published"` → `pub_state: public, verified: true`（`receipts.ts:33` plan 属 `TRUSTED`，`publish-record.ts:60`）。视频号 11:02 对账还是 `reviewing`，Codex 把计划改成 `published` 后，11:32 就成了 public。而 `submission-results.json` 里视频号是 `submitted`，计划 evidence 写着「桌面未验证手机微信播放」；抖音 evidence 写「公开URL尚未另行打开」，同样记成 public。
- Codex 补充：**数据回流按作品 ID 绑上也直接记成 public**（`receipts.ts:88-91`），不核当前是否还公开——绑定不是公开证据。

### 根因 7（Codex 补出，P1）：发布回执去重查全部历史

`record.ts:67-70`：同轮同平台同宿主，只要历史上**任意一条**说法的链接 / 状态一样就复用它。状态 A → B → A 时，第二个 A 复用第一条旧事实，不追加；槽按「最后一条」收敛，结果停在 B。同一请求重放和「新的、值碰巧相同的观察」需要两条不同规则。

### 根因 8（代码推导，未实跑）：投稿后的活动进度会让检查过期

- `check.ts:117-122` 把选中活动的**整个对象**放进 Jev B 请求，B 请求进指纹。本案小红书活动对象在投稿后被追加了 `association`、`form_submission`。
- 前提是存在 B 请求（有原话或例外时才有，`semantic.ts:90`）；本案有原话，条件满足。
- 修正 v1：往新一次检查里加原话，只改变**新检查**的指纹；旧检查按它存的原话重建，不会因此过期（`check.ts:217`）。

### 根因分类小结

| 类别 | 是否成立 | 对应 |
|---|---|---|
| 调用遗漏 | 成立 | 根因 1（漏交审）、根因 2 |
| 接口设计缺陷 | 成立（最该先修） | 根因 3、4、6、7 |
| 状态机问题 | 部分成立 | 根因 1（流转允许，但没有引导到位；已发布后无补批通道） |

## B. 数据流

### 当前

```
创始人在 Codex 对话里说话
  ├─ 粗剪/分镜/样片 → ask/answer_ask → ask_answer (+分镜 storyboard_approval)   ✅ 落账，但不是成片批准
  ├─ 「好 导出成片」  → delivery-confirmation.json                              ❌ 系统不读
  ├─ 「封面就…」      → 05-cover/v002/manifest.json(title_approved)             ❌ 系统不读
  └─ 「发布吧」       → publish-plan.json.authorization / approved_covers       ❌ 被挪作封面凭据

review_inbox：drafting → 写稿段 → 无可 decide 的条目
check：登记失败（错误码丢失）→ 可例外 → override 通过
ego_lite_prepare：旧预检 ✗ → publishFiles ✗；就算放过，封面取自计划而非登记
video_kit：videoDone（登记投影）✗
发布后：计划写 published → 对账当 TRUSTED → public；record 返回的 verified 实为「说法被认」
```

### 建议

```
创始人话语 ──agent decide（原话 + 已展示条目的 item_id/gen）──▶ AutoCrew
                       │  来源如实记（见 C-6）：工作台 = founder；对话 = chat（agent 转述）
                       ▼
           decisions：绑 round + 资产 sha + 动作（已有字段）
                       ▼
           批准齐 → 登记（失败可重试，不重复批准）
                       ▼
     registrationEligibility()：一份「能不能用、用哪几份文件、为什么不行（带码）」
        ├─ check：确定性项 + 语义项；登记类失败一律不可例外
        ├─ verifyCheck / ego_lite_prepare：成片与封面都取登记那份
        └─ video_kit：只存文案，不判发布
                       ▼
     回执：保留现有 已提交/审核中/定时/驳回 语义 + 新增独立的「公开已核」证据维度
```

- **事实来源**：production.json 是唯一批准账本。`publish-plan.json` 是发布意图 + 执行日志；它能证明「已提交」，不能单独证明「已公开」。
- 项目里的 `delivery-confirmation.json` / `manifest.json` 是剪辑方工作笔记，不作证据。

## C. 修复方案（按上线顺序）

前两步就能消掉「每次发布都要例外」；后面几步是同一链路上的正确性修补。

### 第一步：收窄 C-4——检查与打包同源，登记类失败不可例外

1. `registrationState()` 保留 `GateResult.code`（`check.ts:59-62`）。
2. 登记类失败按码分：`not_approved`（从没认 / 撤回 / 正文变了 / 上一轮）、`no_registration`、`registration_pending`、`registered_file_changed`——**全部不可例外**。`basis` 写清缺哪一项，`next_action` 指到对应审阅条目或「重试登记」。不保留「登记例外」这条路：`registration_pending` 里也混着缺字幕、文件变了、事务失败，该做的是重试登记，不是例外。
3. 封面例外与封面比例偏好分开：`cover_registered`（封面是不是登记那对）不可例外；比例槽这类偏好照旧可例外。
4. 打包的成片**和封面**都取登记出口那份文件；成片比较改为按字节（或检查直接记录登记路径），不再要求计划写的绝对路径一致。
5. 本体视频稿的 `ego_lite_prepare` 中间件不再跑旧预检里与计划重复的标题 / 标签 / 字数项；**保留**内容审核和导入历史限制（`pre-publish.ts:325,338`，`verifyCheck` 不覆盖这两项）。非视频稿、未启用 / 被排除的稿、剪贴板、公众号路径不变。顺带统一两处开关：中间件按单条稿是否启用，分发按资料库是否启用（`tool-runner.ts:79` vs `publish.ts:170`）。
6. `video_kit` 不再以 `videoDone` 拦文案保存（它只是存文案）；出包时由登记判定把关。`next_action` 不再指向 `autocrew_video register`。
7. `publish-gate.ts:54` 按码给不同文案：「这条还没认稿」≠「认稿后正文改过 / 重开了」。

### 第二步：补通批准路线（C-2，按 Codex 补全）

1. 视频稿本轮已有**已接受的** aroll / cut 事实时，`drafting` 也出认稿条目（`inbox.ts:385`）。文案只说「已经开拍了，稿子还没认」，**不**说「按录的这版认稿」——没有证据把当前正文和录制版本关联起来。
2. 认稿 / 退回处理器把来源状态写死成 `draft_ready`（`inbox-decide.ts:141,148`），改为取条目展示时的实际状态，仍核正文哈希和代次。
3. `record` 返回的 `next_action` 改成剪辑宿主能直接做的：「调 `autocrew_review_inbox list`，把认稿那件给创始人看」；同时提示：成片要 `review=true` / `mark_ready` 才出审阅条目，封面要成对记录。
4. 已发布的稿：`inbox.ts:405` 目前会藏掉全部审批事项。补批历史数据不走正常条目，走 E 的「证据候选表」。

### 第三步：重试登记、对话可定（C-7 的一半）

- `register_blocked` 条目目前只给「催一下」（`inbox.ts:287`），执行器只认条目自带的动作（`inbox-decide.ts:240`）。在条目上加 `retry_registration` 动作，再把它加进 `CHAT_ACTIONS`。重试不产生第二条批准。

### 第四步：指纹只认内容意图（C-5，按 Codex 修正）

- 定义一份稳定的「活动意图」结构：活动 id、名称、必带主话题、所选子话题、必带 @、投稿期限、首发 / 独家要求等**影响语义判定的字段**都保留；`association`、`form_submission`、`promotion_status` 等执行回执从 B 请求和指纹里一起拿掉。
- 账号、排期、审批、偏好、指令、字幕绑定照旧进指纹。

### 第五步：回执单独一期迁移（C-6，按 Codex 修正）

- **不直接把 `plan` 移出 `TRUSTED`**：那会把所有历史计划观察重算成待核，连带改变 D1 投影、驳回处理、确认提问、把关结论继承、发布台动作。
- 改为在现有槽语义之上**新增独立的「公开已核」证据维度**：已提交 / 审核中 / 定时 / 驳回 / 超时照旧由计划给出；「公开」需要单独证据——能读到的公开页、按作品 ID 的数据回流且有新鲜度、或创始人一句话（视频号手机端）。计划里写 `published` 只算已提交。
- 数据回流绑定不再直接等于「当前公开」（`receipts.ts:88-91`）。
- `record` 返回改为 `{slot_state, claim_accepted, public_verified}`，不再用单个 `verified`。
- 视频号 `/sph/` 短链：链接接受；发布台链接显示和作品 ID 处理一并支持（`desk-rows.ts:77`、`desk-writes.ts:51`）。
- 消费方同步改：发布台指标门槛（`desk-rows.ts`）、数据页（`data-page.ts:44`）独立读计划状态的地方。
- 修根因 7：同一 `request_id` 重放才复用；否则只和**同一流的最后一条**比较，变了就追加。

### 第六步：提交结果不明（C-7 的另一半）

- 现有说法只接受 `public / reviewing / scheduled`（`record-args.ts:99-112`），且要求链接或作品 ID。「提交结果不明」通常两样都没有，单靠槽模型表达不了。
- 新增「提交尝试」记录：平台、发布包、check_id、开始 / 结束时间、状态（进行中 / 已提交 / 失败 / 不明），按 `(content_id, round, platform, check_id)` 唯一。状态不明时出包被拒、发布技能先查作品管理。拦出包挡不住已经拿到的旧包和浏览器直接重交，所以技能规定和记录要一起上。

### C-6（原 C-1）可信确认来源：本轮不上「扫会话记录」

Codex 否掉了 v1 的「全局扫描宿主会话记录核对原话」，理由成立：
- 误判：无关会话里也有「OK」「发布吧」；否定句里包含同样字样；同一句被重复用。
- 漏判：会话记录写盘延迟、轮转、格式变；再次 list 会把时间窗推过有效回复。
- 范围：找到「发布吧」证明不了选了哪组封面。展示给 agent ≠ 用户看到了。
- 隐私与成本：要读无关的整段对话。
- 攻击面：可写日志、路径 / 软链、解析器。

**结论**：这一轮不做任何「看起来防伪、实际不可靠」的认证。保持 10-06 定下的「对话原话直接作数」，但把来源记**如实**：对话决定一律 `source: "chat"`（agent 转述，服务端无法核验），卡片和审计里可见；工作台点击是 `founder`。真正防伪只有两条路：工作台（已有会话认证），或宿主把用户回答直接交给服务端的事件（如 MCP elicitation）——**两种宿主是否支持、能否带上预览，仓库里没有证据，需要单独做一次技术验证**。这与你本次提出的「agent 自写原话不能冒充批准」仍有差距，见文末待决事项。

## H. 已证实 vs 仍缺证据

**已证实（代码 + 本案数据 / 会话记录）**
- 本案没有认稿、成片 / 封面批准、登记；稿件全程 `drafting`；已发布后审批条目全部隐藏。
- 每次 `record` 都返回了 `script_not_approved` 提示；Codex 没照做，也没调用 `review_inbox`。
- 「封面就…」早于 v002 生成；计划里封面凭据挪用了发布授权原话。
- check 认例外，prepare 与 `video_kit` 不认；登记错误码在检查里丢失；封面例外能让未登记的封面进发布包。
- 「认稿已失效」在从未认稿时也出现。
- 冻结机制挡住了「认稿后改正文让成片批准失效」的正常路径。
- 计划里的 `published` 被当成可信公开；数据回流绑定直接等于公开；`record` 的 `verified` 实为「说法被认」；回执去重查全部历史。
- 对话认稿处理器的来源状态写死为 `draft_ready`；`stage-guard` 不拦创始人认稿。

**代码推导、未实跑**
- 投稿后活动回执让小红书检查过期（根因 8）。
- 本体视频稿修好登记后，中间件的阶段门还会拦 `drafting` 稿。

**仍缺证据**
- Codex 当时能否拿到写稿认领令牌去交审。
- 这条稿为什么停在 `drafting`：需要看 10-13 的写稿会话（claude-code）。
- 两种宿主是否支持把用户回答直接交给 AutoCrew 的事件（MCP elicitation），以及能否带预览。
- 四个平台是否真的公开可访问：按要求没有访问平台。

**待你决定**
- 对话确认的防伪：本轮保持「原话直接作数、来源如实记」，不做会话记录扫描。是否要另开一次技术验证，看宿主原生确认事件能否在不加点击的前提下做到真防伪。
