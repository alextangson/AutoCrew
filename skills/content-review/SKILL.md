# 文案审核

先读目标稿全文、本次要求、实际材料与已有审稿结果。判断是否遵循用户规划、主张是否站得住、表达是否适合读者；每个问题要指出原文位置与原因。

## 正式写作链

新稿或正式修订按 `write-script` 走 `autocrew_workflow prepare → 选角 → autocrew_writer pack → 宿主写作 → submit → submit_status`。审稿与受众点评在交稿的异步流程里完成，不能用机械扫描代替。

- `review_required`：按问题范围修订，保留无关内容；结构或规划缺项可调整相关段落，再增加 attempt 提交。
- `accepted`：AI 审稿未发现阻断项，仍要展示建议与实际受众结果，不等于作者认可。
- `accepted_with_issues`：保留草稿，说明残留问题与建议处理；不能称合格。
- `accepted_unreviewed`：说明未完成语义审稿的原因，不能写“已过审”。

回执的 `audience_review` 是独立事实：`reviewed` 时按 result 解释哪类读者会停留、在哪里流失、可怎么修改；`unavailable` / `skipped` 时报告 reason。没校准画像不伪装成受众已验证。负面受众点评是建议，不能强迫写手改成统一套路，也不能将模拟点评当作真实用户测试。

## 单独检查已有稿

`autocrew_content {action:"get", id}` 读取当前版本；`autocrew_editorial {action:"inspect", content_id}` 核对正文版本与反馈。需要基础检查时调 `autocrew_review {action:"full_review", content_id}`：它只检查机械文字问题与格式，不给可靠的 AI 痕迹判断，不替作者批准，不给文章“质量总分”。

用户只要求点评时，宿主可依据全文、材料与要求给出逐条编辑判断，明确这是本次对话的审阅，不能冒充未执行的产品后台审稿。用户要求改稿再转写作包与提交链，pack 带原 content_id、topic_id、platform 与 force:true；不要为检查一篇稿偷偷生成新版本或改变批准状态。

## 判断标准

- 本次规划：读者、目的、主张、提纲、必须包含与避免的内容有没有兑现。
- 事实与论证：证据对象、时间、范围和上下文是否支撑主张；数字命中材料不代表说法成立。缺少依据要指出，不凭空补数字、案例、亲历。
- 表达：重复、空话、跳跃和过度包装是否影响理解。词表、段落长度、没有反问或 CTA 本身不是错误。
- 受众：读者得到什么、哪里可能看不懂或失去兴趣。说明推断依据与限制，不编造“爆款概率”。

每项用“问题原句 → 为什么影响本稿 → 建议怎么改”表达。记录用户对结果的真实反馈用 `memory-distill`；模型给自己的好评不能写入用户采纳。发布前另走 `pre-publish`。

## GUI

本节仅供 AutoCrew 工作台加载；纯 MCP 宿主执行上文。

1. 用 `get_draft` 读当前全文；不确定对象时先 `list_drafts`。结合上下文已有写作要求与真实材料，检查规划、事实、论证和表达，不给虚假的 AI 痕迹分数或质量总分。
2. 当前可见 `audience_review` 时，用稿件 id 请求受众停留点评，说明哪类人可能停留、哪句可能流失。画像未校准或审稿失败时如实披露；模拟意见不能当真实用户测试。
3. 用户只要求审阅时给具体问题与建议，不改正文、不替作者批准。用户要求修改时，有当前修改焦点就用 `revise_focus` 出提案；否则按问题范围用 `revise_draft`，不为审稿强制添加 CTA、反常识问句或数字。
4. 改稿后的结果不沿用旧的审稿结论。模型未见的材料要说明缺口；不能把文本检查通过说成已批准发布。
