# 视频发布与活动回填

同一条视频的四个平台共享已批准成片，各自保留标题、文案、封面、活动、排期和结果。
所有网页访问、搜索、上传、表单回填和核验统一用 `ego-browser`（ego lite）。先读该 Skill
及用户的 managed skill overrides，按它当前提供的 API 操作；不调用旧版浏览器方法。

## 本用户的发布默认值

- 用户于 2026-09-25 明确提供：四个平台统一昵称为 **哈姆雷鹿**。将其作为目标昵称和表单
  默认资料，不重复询问已知昵称，不自行改成近似字，也不执行账号改名。发布时仍核对真实账号
  与已有公开主页/稳定 ID；页面昵称不同则核对差异，不能仅凭相近昵称认定账户。
- 作品/笔记 ID 由 agent 在公开后通过 ego lite 从作品管理、公开页面或规范分享链接自行取得，
  核对账号和视频身份后填写；不要默认让用户找 ID。定时/审核中只等待，不把提前拿到 ID 当公开。
- 活动子话题由 agent 读取本条视频内容后自动选择最符合核心内容的一个，并在发布计划记录理由，
  不随机选择、不把全部子话题堆上，也不把常规话题选择变成新的人工审核节点。

## 稿件与文件来源

- **AutoCrew 稿件**：用 `autocrew_content` 读取当前版本；发布前把关用 `autocrew_publish`
  `action=check`（见下文第 8 步）。`ego_lite_prepare` 只准备发布包，prepare 不代表上传或
  发布成功。各平台封面比例**以 check 为准**，不看平台编辑器的默认裁切框（编辑器对横屏视频默认
  给 4:3 框，不代表该平台要 4:3）。
- **个人视频项目**：从 `personal-ip-video-loop` / `video-project-lifecycle` 交付时，读取
  项目现存的成片与双尺寸封面审批、文件清单和哈希，引用 `07-delivery/` 与已登记封面。
  不为发布复制成片，也不强制新建 AutoCrew 稿件；保存可恢复的本地发布记录即可。
- 恢复同一任务时沿用原来源，不能因 MCP 断连改用未审核本地文件。AutoCrew 不可用则报告
  连接缺口；已保存且可验证的原发布包可继续获授权的浏览器工作，产品回写记为待同步。
- **断连或内容不在 AutoCrew**（check 跑不了）：在最终点击前停下来告诉创始人；只有创始人明确说
  「这次不检查直接发」才继续，并在发布计划与回执里标「发布前未把关」。
- 缺少成片/封面批准、真实文件或明确目标账号时，只补缺项；封面通过不等于发布授权。

## 发布前：活动、排期和一次汇总

1. 读取完整脚本/成片摘要，按 [campaigns-and-followup.md](references/campaigns-and-followup.md)
   核查四个平台当前官方活动。每次核对有效期、题材、准确话题、官方账号、报名入口、
   首发/独家要求和发布后收集表；不要把上月话题或搜索摘要当当期规则。
2. 上传前备齐各平台标题、完整描述、主题关键词、活动主/子话题、双尺寸封面、声明和带时区排期，
   保存到同名项目 `06-publish/`。活动必须符合实际内容：不伪造第一人称体验，不为活动改稿。
   无合适活动时正常发布。尚缺的平台信息单独标记，不拖住其余已备齐且获授权的平台。
3. 从 [publish-plan.example.json](references/publish-plan.example.json) 按实际任务建立
   `06-publish/publish-plan.json`，替换示例、删除不用的项。已有记录就地更新，不覆盖回执。
   每个平台独立一个条目；若关联 AutoCrew，使用自己的 `content_id`，不能四平台共用一个。
4. 用户给了排期就记录带时区的具体时间；没给时间则不猜，也不默认立即发布。检查计划
   公开时间是否在活动投稿期内，另记收集表截止期；未知截止时刻不能凭空补成 23:59。
5. 同一批四平台发布使用一个 ego task space，保存实际 `spaceId` 和页面 label，按 ID 恢复；
   不每个平台另建空间。发布包中的历史 `taskSpaceName` 仅作关联信息，不改变一任务一空间。
6. 核对登录账号。扫码、验证码或用户接管时用当前 `task.handOff()`，用户明确恢复后才
   `takeOverTaskSpace(id)`。不记录 Cookie、二维码或验证码。公开账号名/主页只在匹配与
   表单必需时保存在项目私有记录，不扩散联系方式等私人信息。
7. 按下文执行流程上传和批量填写；页面允许时在上传期间填表，不必等上传完成才开始。
   选择原生话题/@账号候选、活动组件；单纯出现 `#文字` / `@文字` 不代表已关联。
   提交前必须确认真实上传与所需转码已完成。缺少声明、商业属性等事实时集中补问，
   不擅自承诺独家、收费推广或品牌合作。
8. **发布前把关**：一次确认汇总前必须跑 `autocrew_publish action=check`，带 `content_id`、
   `plan`（`06-publish/publish-plan.json`）、`founder_quotes`（本次对话里创始人关于这次发布的
   原话，逐字，一句不漏）和 `instruction_id`（创始人贴来的网页指令末行「指令编号：ins-…」；没有就不传）。
   - 返回的 `summary_table` **原样**贴进下面的一次确认汇总，不改写、不删行；
   - verdict=block 的平台不得提交：改计划后重跑。创始人明确要破例时，带
     `overrides[{platform, rule, founder_quote}]`（rule 取被拦项的 rule 名，原话逐字）重跑，汇总里会显示「按你原话例外」；
   - 计划任何字段改了（标题、文案、封面、排期、账号、平台）都要重跑 check；
   - 语义检查「没跑成」不挡发布，但要在汇总里照实说；
   - 创始人说了新的长期偏好（如「小红书以后横竖都传」「B站标题别带表情」），用
     `action=propose_preference{kind, platform?, value, founder_quote}` 提议，创始人在工作台确认才生效。
9. 汇总四个平台的账号、标题、封面、准确发布时间、活动及回填目标，供用户**一次确认**。
   点击最终发布/定时投稿前需本次明确授权；已有覆盖同一发布件的确认就继续，不重复问。
   用户只要草稿就停在草稿。报名/表单有额外义务时先准备具体内容，只澄清增量范围。

## 主题关键词与长尾搜索

- 以视频实际主题为主，活动话题为辅。上传前选好核心主题、准确产品/术语、用户问题和方法词；
  在平台当前数量及字数上限内尽量补足有区分度的相关词，不机械填满、不堆同义词或无关热词。
- 各平台分别适配，不把同一串标签硬贴四遍。保留必需的活动主/子话题，其余位置优先主题词；
  准确产品名和自然中文优先。关键词也可自然写入标题和描述，不能夸大视频内容或承诺流量提升。
- 在发布计划逐平台记录拟用词、实际原生关联词和未采用原因。话题插入后读回完整描述，
  检查是否插在句子中间、重复文字或遗漏末尾；修正文案时保留原生话题节点。
- 已提交稿件补词，先检查平台支持的编辑方式及对审核、定时的影响，保留原排期；不为补词重新上传
  或重复投稿。用户说已手动发布时先记录为用户报告，获准恢复后只查作品管理核验，不再次提交。

## 浏览器执行：批量操作、关键节点检查

默认顺序：备齐发布包 → 上传期间填表 → 批量完成并检查 → 单次提交 → 保存回执。
优先完成一个平台的填写、核验、提交和回执再切换；上传等待期间可处理其他已准备好的平台，
但不得让多个表单混淆账号、素材或提交状态。活动研究与文案设计前置，临提交只补真实新增条件。

- **优先结构定位。** 首次用精简 snapshot 获得控件依据，使用 ref、语义定位或已观察到的选择器。
  对同页已知控件，在一轮调用内连续填写标题、描述、话题、声明和排期；仅在下一步依赖中间结果时观察。
  页面变化后刷新受影响区域，不每点一下都抓整页，也不在同一节点默认同时取 snapshot 和截图。
- **截图用于视觉问题。** 封面及裁切需视觉核验；画布、无语义控件或点击遮挡时才切到截图与坐标。
  一张当前截图可支持同一稳定界面的连续操作，弹窗或布局变化后再观察；不沿用过时坐标。
- **同类故障及时换方法。** 一次失败后读当前状态判断是否已生效。确认是嵌套框架、Shadow DOM、
  `wujie-app` 遮挡或只读日期框，就换正确的控件上下文、可见坐标或 ego 文档支持的页面内操作；
  不重复同一种失效点击，不反复用 fill 写只读日期框，不盲目增加等待时间。
  不通过修改框架内部状态、伪造完成值或未核实的私有发布接口绕过页面校验。
- **等待可观察结果。** 用上传进度、完成标记或控件可用状态判断，优先条件等待；无变化不密集轮询。
  只有确认失败且前次提交未发生才重试。用户已上传的文件先检查，不能直接重新上传。
- **提交前集中核验。** 统一核对账号、素材、完整文案和原生话题、声明、封面、时区与排期、警告。
  已检查且未改变的项目不重复截图；草稿恢复后重读排期，不假定平台会保存。
- **提交后只取必要回执。** 成功提示若未含日期或作品身份，则查看管理页补齐；一旦证据足以证明本条
  状态与排期就保存并转下一平台，不重复跨页面确认。结果不明先查管理页，不再点击最终提交。
- **用户接管是硬停止。** 停止该空间及同一外部操作，保存已完成项、未完成项和空间 ID；
  只有用户明确交回后恢复。不能把接管当成普通点击故障绕过。

## 发布前必须告知本次活动计划

点击任何平台的最终发布或定时投稿前，先在对话中向用户说明本次四个平台的活动计划，
不能只写入本地 JSON 或等发布后补报。逐平台列出：拟参与活动的准确名称、官方链接、
所选主/子话题、与本片内容的匹配理由、投稿期限是否覆盖排期、报名方式及公开后回填事项。
无匹配活动写「普通发布，不参加活动」；尚未核实写「待核实」并说明具体缺口，不能写成无活动。
普通标签与平台官方活动分开表述。仅拟定或带了文字标签不能称为「已参与」。

这份说明并入原有一次发布汇总，不新增重复审核节点；已有授权覆盖同一发布件就继续。
新增付费、独家/首发承诺、额外隐私字段等实质条件时，只确认新增范围。告知后活动发生变化，
在提交受影响平台前补充说明。发布后按实际回执报告已关联的活动、待回填表单和未成功项目。

将告知时间、对话中说明的计划摘要及后续变化保存在 `06-publish/publish-plan.json` 的
`campaign_disclosure`，恢复任务先比较活动计划是否变化，不把旧说明套用于新活动。

## 提交与真实状态

获授权后，**最终点击前逐字段读回页面，与发布包 / 通过 check 的计划比对**：账号、标题、文案、
标签、排期、活动逐项核对；封面按上传槽逐张截图核对实际裁切（B站封面设置里的 16:9「个人空间封面」
框由平台从 4:3 裁出，必须在该弹窗里确认标题没被切掉并截图留证）。有出入就停下，改完重跑 check。
每个平台只点击一次最终提交。
保存稿件 ID、回执时间、页面证据和真实状态：

- `scheduled`：平台已接受未来排期；不是公开发布。
- `submitted` / `reviewing`：已提交/审核中；不能填要求公开作品的活动表。
- `published`：作品确实公开可访问，且账号、标题/视频与本任务一致；记录规范 URL 和作品 ID。
- `rejected` / `failed`：保留平台原因；不把其他平台一起标成失败或成功。
- `submission_unknown`：点击后结果不明；先查作品管理，不重复点发布或重新上传。

出发布包用 `autocrew_publish ego_lite_prepare`，带上 check 返回的各平台 `check_ids`：检查过期（计划或文件改过）或被拦的平台不会出包，按报错重跑 check。发布结果以项目发布计划 `06-publish/publish-plan.json` 为准（每个平台一条，带上 check 返回的 `check_id`，**点提交的那一刻按平台写 `publication.submitted_at`（带时区的实际提交时间，不是定时公开时间）**；没有实际提交时间、没带有效检查、或检查之后又改了这个平台的内容再提交的，卡片都会标「发布前未把关」且事后补检抹不掉），AutoCrew 每分钟对账读取：每条稿每一轮每个平台只有一个发布槽，最新的记录算，被驳回的不算已发布。确认公开作品后可以 `autocrew_content record kind=publish platform=… url=…`（或 item_id）报一次：它只记成「待核」，由同平台的发布计划记录 / 数据回流顶掉或创始人在卡片上确认，不会直接改成已发布；不要调用 `confirm_published` 代创始人标记。产品断连时保存待回写记录，不虚构工具成功。

## 定时发布后继续完成

读取 [campaigns-and-followup.md](references/campaigns-and-followup.md)，完成调度、公开状态
核验、活动关联和表单回填。用户已于 2026-09-25 明确希望 AI 完成已授权活动的发布后回填：
对已确认发布件中列明的活动/表单，使用有来源的必要资料完成提交，不再例行索要二次确认。
目标、额外隐私资料、付费、独家条款等实质范围改变时，补足缺失授权后再执行相关部分。

完成标准：各目标平台有真实结果，所选活动关联有证据，要求的表单有成功回执，或明确列出
单个平台/表单的阻碍。**表单提交成功不等于官方批准投流，更不等于流量到账。**

状态、活动来源、发布件、作品链接、回填内容和脱敏回执都保存在 `06-publish/`，随项目归档。
归档时保留尚未完成回填的轻量本地记录与调度指向，按 lifecycle 规则清理大文件；
不把“必须先发布”加成 NAS 归档门槛。

Skill 本身不定时唤醒。只有宿主自动化工具返回真实 ID 并记入计划，才能报告后台跟进已启用。
需登录时保留准确待办；没有具体视频与排期时只配置流程，不创建空轮询。
一次浏览器工作结束按 ego Skill `task.finish({keep:[]})` 收尾；交给用户登录时保持 handoff，
不关闭登录页面或自行恢复。未来独立唤醒沿用仍有效的空间，否则为该次跟进新建一次并记录。
